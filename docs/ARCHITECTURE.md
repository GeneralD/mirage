# Architecture

macOS menu-bar app: webcam → real-time Metal shader effects → virtual camera. Clean Architecture in the lyra style, with SwiftPM targets enforcing layer boundaries at compile time and every physical element behind a port so the test suite is deterministic.

> This is the canonical architecture reference. `.claude/CLAUDE.md` keeps a short summary and points here; the **enforceable** boundaries live in `.claude/rules/architecture-boundaries.md` and `.claude/rules/physical-abstraction.md`.

## Architecture Decision Record

**Context.** The product replaces the discontinued Snap Camera on macOS: webcam frames are processed by GPU shaders and served to any video-calling app as a virtual camera. Effects must be loadable at runtime from community-authored `.lens` packages (MSL source compiled with `MTLDevice.makeLibrary(source:)`), so untrusted GPU code is a first-class input. The only sanctioned virtual-camera mechanism is a CoreMediaIO Camera Extension (macOS 12.3+; DAL plug-ins were disabled in 14.1), which runs sandboxed in a second process, so a host → extension IPC is unavoidable. The author's lyra codebase proved a pattern — one SwiftPM target per layer slice, swift-dependencies DI, every OS boundary a port, a shared TestSupport with event-driven waiting — that keeps a large module graph testable without flaky tests; the sibling decoy project proved the CMIO/System Extension/Mach-port plumbing. Solo developer, rich domain (frame pipeline, effect lifecycle, GPU failure policy, IPC), AI-assisted development that relies on tests as the specification.

**Decision.** Clean Architecture with the lyra layer vocabulary (Entity → Domain → UseCase → Repository → DataSource/DataStore → Gateway, plus Interactor → Presenter → View/Router lanes for the GUI). swift-dependencies for DI with one wiring target per process. All physical elements (camera, GPU, compiler, IOSurface, Mach, System Extension, CMIO stream, files, watch, clocks, host time, randomness, defaults, logging, display link) are Domain ports with fake doubles in a shared `TestDoubles` target. No actors on the frame path; frame flow runs on an injected `FrameExecutor` and surfaces travel as pooled, generation-tagged leases. The Xcode project is a thin xcodegen shell that embeds the Camera Extension; all logic is SPM. Product name is confined to three files.

**Consequences.** Tests are fully deterministic and run in parallel without a GPU; the module count is high (≈50 targets) and every new module touches `Package.swift`, DI and docs (the checklist is mandatory). The real GPU and the real extension are exercised only in a separate local test job and a manual verification lane. Zero-copy frame transport depends on the `SurfaceToken` + Mach-port design surviving the M0 spike; the fallback is one copy per frame. Renaming the product is a three-file change plus profile re-issue.

## Frame Path

```text
AVCaptureSession ──(CaptureSessionGateway, serial queue)──▶ CameraDataSource ──▶ CameraRepository
   ▼ FrameRef + SurfaceToken
FramePipelineUseCase  (LatestFrameSlot → tick() on FrameExecutor → one effect pass in flight via WorkRunner; a busy tick drops its frame; any failure sends the input)
   ├─▶ EffectRuntimeRepository ──▶ ShaderCompilationDataSource ──▶ ShaderLibraryGateway (makeLibrary(source:))
   │   (orchestrates, no state)    ├▶ GPURenderDataSource ──▶ GPUGateway (encode / commit / completion)
   │                               ├▶ EffectRuntimeStateDataSource (in-process cache, newest wins, session clock; hops onto FrameExecutor)
   │                               └▶ BundledEffectDataSource (the default effect's MSL, a string constant)
   │   the frame that goes on (output, or input on failure) fans out: sent first, then presented; its lease ends with the later of the two
   ├─▶ VirtualCameraRepository ──▶ FrameTransportDataSource ──▶ MachGateway (IOSurface mach port, MOVE_SEND)
   └─▶ PreviewSink (host, same frame, completion ends the lease) ──▶ PreviewRepository ──▶ PreviewDataSource ──▶ PreviewGateway (MetalKitPreviewGateway: one compute blit into the view's CAMetalLayer drawable)
                                   ║ process boundary (sandboxed Camera Extension)
ExtensionRelayUseCase ◀── FrameReceiverRepository ◀── FrameReceiverDataSource ◀── MachGateway (check-in, receive: frame / hello / dead-name)
   └─▶ StreamOutputRepository ──▶ StreamOutputDataSource ──▶ CMIOExtensionGateway (CMIOExtensionStream.send)
   (host lost → SlateSchedule: black frames from a per-episode slate surface, ticked by FrameScheduler, until a newer real frame arrives)
```

The host also keeps a presence port alive toward the extension and reconnects on its own when the extension goes away (see *Host absence and slate* and *Host reconnect* below). Pixel buffers never cross a layer as `Data` or as raw `IOSurface`. The host and the extension each own a `SurfaceRepository`; a surface only crosses the process boundary as a Mach port and is re-leased on the other side.

Delivery stages: **M0** spike (pass-through to Zoom via the real extension) → **MVP-A** one bundled effect end-to-end in the dev harness and the loopback (camera → GPU → preview; the extension path is M0's) → **MVP-B** runtime `.lens` loading + hot reload + menu switching (epic #42, landed; the timed run on a device is Lane 1's) → **MVP-C** parameter UI → **MVP-D** pass-through on failure + auto-disable. Later: Vision face landmarks / person segmentation inputs, GLSL (Shadertoy) import, URL/Git import, gallery.

## Key Design Decisions

**Rename-safe naming.** The product name appears in exactly three files: `README.md`, `project.yml` (`name`, `PRODUCT_NAME`, bundle IDs) and `Sources/Entity/ProductIdentity.swift` (display name, host and extension bundle IDs, Mach service name, log subsystem, virtual device UUID — plain literals, because `project.yml` and the provisioning profiles need the same literal strings and `scripts/check-service-names.sh` compares them textually). Module, target, type, file and directory names are role names. The shells' `Info.plist` and entitlements necessarily carry bundle IDs, so they are **generated** by xcodegen from `project.yml` (`info:` / `entitlements:` properties) and gitignored — never hand-written. The one hand-written plist, the dev harness's (*Dev harness* below), carries a role-named bundle ID and no product name. Renaming = editing those three files + re-issuing the two provisioning profiles (bundle IDs and the Mach service name are baked into them — an Apple constraint, not a code one) + `gh repo rename`. `make check` fails if the product name string appears anywhere else under `Sources/`, `Tests/`, `Apps/` or `Tools/` (Swift and Metal sources, every file under `Tools/`, file and directory names). `Examples/` (the sample `.lens` packages) is outside that scan and is kept clear of the name by hand: `grep -rli '<name>' Sources Tests Apps Examples` finds only `ProductIdentity.swift`.

**Gateway modules for every OS boundary (lyra, not decoy).** decoy hid OS types behind inner ports inside adapters; here each boundary is its own `*Gateway` module consumed at the DataSource layer (the execution-context ports — `frameExecutor`, `frameScheduler`, `workRunner`, live in `DispatchExecutorGateway` — are the exception: the UseCases run the frame path on them, and the key-path lint names them), so the import lint can draw a hard line: AVFoundation, Metal, MetalKit, IOSurface, CoreMediaIO, CoreMedia, CoreVideo, SystemExtensions, AppKit and `os` are importable only in Gateway modules and the View/Router/App lane.

**No actors on the frame path; tokens instead of surfaces.** decoy hit a Swift 6.3 crash passing `IOSurface` across an actor boundary and fell back to `Data` frames (up to four full copies per frame). Here frame callbacks run synchronously on the `FrameExecutor` port (live: one serial queue), UseCase frame state is a single-threaded state machine (no locks in UseCases), and pixel storage is referenced through `SurfaceToken` — an `(index, generation)` value issued by `SurfaceRepository` / `SurfacePoolDataSource`. The generation is what makes the token safe without a scoped wrapper: a token whose generation no longer matches the slot resolves to nothing, so a double `release` or a use after release is detected (`release` returns `false`) rather than touching the slot's next tenant. Tokens are process-local and never serialized; a surface crosses the process boundary only as a Mach port. Property test: after stop, `liveCount == 0`; any allocate/release sequence never double-frees. To be validated in the M0 spike; fallback is a single copy at the transport.

**Latest-frame slot + tick, not per-frame fan-out.** Capture callbacks only overwrite a `LatestFrameSlot`; the pipeline consumes it on `FrameScheduler.tick()` with an in-flight cap of one effect pass (see *Effect stage* below). Heavy encoding never runs on the capture callback, and interleavings are enumerable in tests (`ManualFrameExecutor.drain()` + seeded `forAll`). A TSan job (`swift test --sanitize=thread`) runs nightly.

**Effect stage: one pass in flight, two leases, pass-through without memory.** Owner: `FramePipelineUseCase`. A tick takes the slot's frame, leases an output surface of the same descriptor from `SurfaceRepository` and starts `EffectRuntimeRepository.apply(input:output:frameContext:)` through the `WorkRunner` port; the answer hops back onto the `FrameExecutor`, where the pass (`EffectPass`: input, output, and the stop count its run started under) lives. *In-flight cap = 1:* frames that arrive while a pass runs wait in the slot (newest wins, as always), and a tick that finds a pass still running drops the frame it took as `.inFlightCapReached` instead of holding it across the tick — so every frame a tick takes ends as exactly one send or one counted drop (or is abandoned by `stop`), which the seed property checks as a conservation law. *Leases, each released exactly once, and only the answer ends a pass:* on success the input is released at the answer and the output goes on; on any failure the unused output is released at the answer and the input goes on unchanged. The frame that goes on is released once the sink and the preview are both done with it (*Preview fan-out* below). An output that cannot be leased (pool exhausted, or an allocation error) drops the frame as `.poolExhausted`. *No failure memory:* every frame is judged on its own answer; consecutive-failure counting and auto-disable belong to `EffectHealthPolicy` (MVP-D). *Stop abandons the pass; it cannot cancel it:* cancelling cuts no GPU work short, so the live runtime may still read the input and write the output after `stop()`. `stop()` first bumps a stop count (a `CurrentValueSubject`, so the bump is visible at once from any context), and an answer from a pass started under an older count only ends the pass — even one already queued on the executor ahead of `stop()`'s cleanup — so nothing is sent after `stop()`. A pass carries the count its run's `start()` read, which every tick of that run is handed, never a count the tick reads itself: the live ticks fire on the executor's queue while `stop()` runs on the caller's thread and bumps the count before it waits for the tick under way, so a tick reading the count would adopt the new one and send after `stop()` (or into the next run). The abandoned pass keeps both leases and the in-flight cap until its answer, which releases both with nothing sent, shown or counted; the cleanup's `releaseAll()` waits for that answer and for every frame still on the preview (and is left out once a restart owns the pool), and a restarted pipeline's ticks drop as `.inFlightCapReached` while the abandoned pass is still out. `PipelineStats` counts every drop by reason (the extension's slate drops included, so the reasons add up to `framesDropped`) and effect outcomes by failure kind. The effect half of that bookkeeping (`noteEffect`, `effectsFailed`, `effectSummary`) is host-only policy and lives in `FramePipelineUseCase`; `note`, `noteReceived` and `summary` stay in `Entity` because both UseCases use them and neither may depend on the other. The developer log carries a per-second `effect` line (`applied=… failed=… <kind>=… capDropped=…`) next to the `pipeline` summary. Drop lines are deduplicated per source — the effect stage and the transport each log a reason only when it changes, and `start` and `.connected` make every reason news again — and the operational failure behind a drop (an exhausted pool) reaches the error log by the same rule, once rather than once per frame. The pipeline never calls `prepare(effect)` either: `EffectCatalogUseCase` does (*Effect catalog* below), and until it has prepared anything the runtime prepares the bundled effect on the first `apply` (*Effect runtime* below).

**Preview fan-out: the frame that goes on is sent, then shown; its lease ends with the later of the two (epic #14, D9).** Owner: `FramePipelineUseCase`, through the `PreviewSink` port (`\.previewSink`, the Repository-layer port next to `VirtualCameraSink`). The pipeline owns both leases of a pass, and the frame that goes on — the output on success, the input on any failure — is handed to `VirtualCameraSink.send` and then to `PreviewSink.present`, and released once both are done with it, exactly once. The send returns synchronously, so presenting after it reduces "both" to the preview's completion: that completion may run on any thread and at any point, so it hops onto the `FrameExecutor` and the lease ends there. With no view attached the live `PreviewDataSource` queues the frame on the executor and completes it in that job, after `present` has returned; `InMemoryPreviewSink(holding: .onceAttached)` completes inside `present` itself, the stricter case, and the pipeline's tests run on it (`LoopbackRig(preview: .rendered)` runs the live timing). A frame the sink refuses (not connected, queue full) is still shown and its drop counted as before: the preview is the host's own view of the camera, not a mirror of the link. The preview holds that lease and nothing else — the in-flight cap ends at the answer — so a preview slower than the camera delays no pass and no send; what it costs is pool surfaces, which `PreviewDataSource`'s latest-wins bounds at two (one drawn, one waiting) within the live pool of eight, and which in the pipeline's pool of four tests runs the pool out: the camera is refused or the output lease drops as `.poolExhausted`, and nothing leaks. `stop()` does not abandon a frame already on the preview (it was sent before the stop); its pool reset waits for every such frame as it waits for an abandoned pass — an executor-confined count of frames on the preview — and the last completion or answer to arrive after the cleanup runs it, unless a restart owns the pool by then. The conservation law is untouched: the preview neither sends nor drops, so every frame a tick takes is still one send, one counted drop or one abandoned pass. Alternatives not taken: presenting before sending and joining two completions with a per-frame count, which only an asynchronous `send` would need; and skipping a presentation while an earlier one is outstanding, as the harness's retired solid-frame UseCase did — the DataSource's latest-wins already bounds what the preview holds, and the pipeline would duplicate that policy. Proven by `FramePipelinePreviewTests` (late completion, sink first, no view attached, stop and restart with a frame on the preview), a 50-seed property over emit / tick / effect answer / send / preview completion / attach / stop / restart, and `FramePathIntegrationTests` running the real `PreviewRepository` / `PreviewDataSource` over `FakeGPUGateway` + `FakeShaderLibraryGateway` + `FakeTextureCacheGateway` + `FakePreviewGateway` on the loopback's host side.

**Two time sources, one rule.** Sleeping, debouncing and timers use `\.continuousClock` (lyra); PTS uses `HostTimeProvider` (mach uptime, required by `CMIOExtensionStream` `.hostTime` clocks — decoy observed Zoom freezing when PTS was `0` or "now"). To keep `TestClock` and `FixedHostTime` from disagreeing, slate frames derive PTS as `base + n × (1/fps)` from one captured base, and uniform `time` is `PTS − sessionStartPTS` in seconds (`EffectSession`). No wall clock anywhere.

**Runtime MSL compilation through our own pipeline, not Core Image.** `CIKernel(source:)` is deprecated and Metal `CIKernel`s need pre-built metallibs; `MTLDevice.makeLibrary(source:options:)` is the only runtime path. `ShaderCompilationDataSource` (port `ShaderCompiler`) prepends the prelude (`Uniforms`, hash/noise helpers) with `#line` so diagnostics map back to the author's lines, and runs the compile off-main inside a `WorkRunner` item (the fake gateway records the thread and fails the test otherwise). It caches nothing — the cache and "newest wins" are `EffectRuntimeStateDataSource`'s — and cancellation does not shorten a compile: the caller stays suspended until the compiler finishes and receives the real result (pinned by `ShaderCompilationDataSourceTests`, mirrored by `FakeShaderCompiler`), so dropping a stale handle is the state's decision (`EffectRuntimeStateDataSource` compares tickets), never a side effect of cancelling its task. It asks `GPUGateway` for a fresh context per compile: compiles are rare, the compile needs only the device, and the handle it returns (the pipeline state) dispatches on any context of that device, so no context is shared across concurrent compiles and no lock is needed. **`#line` diagnostic mapping:** the assembled source is the prelude, `#line 1 "effect"`, then the author's source verbatim (`ShaderSourceAssembly`, pure), so the compiler numbers the author's lines from 1 under the file name `effect`; `MetalGateway smoke` proves it on the real compiler on every `test-gpu` run (a syntax error on the author's third line comes back as `effect:3:`, not as its line in the assembled source). On top of that the DataSource rewrites any location still given against the assembled source: `program_source:<n>:` inside the author's part becomes `effect:<n − offset>:` — the safety net should a compiler ignore the directive, property-tested over 50 seeds of source length and error position — and inside the prelude becomes `prelude:<n>:`, so the note under an author's redefinition of `hash` says where the original lives. Only a location that opens a diagnostic line is rewritten: the compiler echoes the failing source line verbatim, so `program_source:<n>:` inside that excerpt or inside a message is the author's text and is kept. **The prelude** declares `Uniforms` (mirrors `EffectUniforms`; `static_assert(sizeof(Uniforms) == 24)` turns a drift into a compile error of every effect), `hash(cell, timeStep, seed)` (white noise in [0, 1) at 24-bit resolution from integer avalanche rounds, so bit-exact against the Swift twin) and `noise(p, time, seed)` (value noise, trilinear over the hash lattice in space and time with smoothstep weights; IEEE adds and multiplies, so within one 8-bit step once the GPU fuses a multiply-add); internal helpers live in `namespace prelude`, and the prelude never defines the entry point. `HashNoiseReference` (`Tests/TestSupport`) is the Swift twin, operation for operation; the `hash-noise parity` GPU suite compares every pixel of a 256 × 256 image for seed 0 and another seed under the GPU suites' single tolerance, and the hash's 24 bits bit for bit.

**Effect runtime: a Repository that orchestrates, over a state confined to the executor (epic #14, D1 / D14).** Owner: `EffectRuntimeRepository` (`EffectRuntimeRepositoryImpl`, a stateless struct); memory: `EffectRuntimeStateDataSource`. *Where the state lives.* The compile cache, the selection, the ticket counter, the callers waiting for the selection and the session clock must change together, in one step, so they are confined to the `FrameExecutor` (thread confinement on a serial executor): there is no lock, which the lint forbids above the Gateway, and no actor, which the frame path avoids and which would take `ManualFrameExecutor.drain()` away from the tests. A Repository does not reach for the executor, so the state is a DataSource — the precedent is `SurfacePoolDataSource`'s slot bookkeeping and `GPURenderDataSource`'s hop onto the executor — behind the `EffectRuntimeState` port, whose every call hops there itself, decides in one step and hops back. A UseCase was ruled out because it sits above the Repository (the Repository would have to call upward, or the pipeline would hold a second UseCase for one runtime: UseCase → UseCase); a `DataStore` is, in this repo, persistence over a Gateway (`PreferencesDataStore`), and these transitions are not storage. The price is one more module, and an `EffectTicket` crossing the port so that "newest wins" is decided in the state while the slow compile runs in the Repository. The Repository resolves `effectRuntimeState`, `shaderCompiler`, `gpuRenderer`, `bundledEffects`, `workRunner` (the lifetime of the compile an `apply` starts) and the two logs; its suite is wired without any executor, so one that reached for it would meet the unimplemented default. *The cache* is keyed by `(source, compile options)` — a `Hashable` key of the two, so a hash collision still compares the sources — and never by the effect's name; only successful compiles are kept, so a broken source compiles again when it is prepared again. It lives in process only: a cache on disk, which would need a device id, an OS version and a `RuntimeEnvironment` port to supply them, is deferred to Later (epic #42, D12, which supersedes the plan of epic #14, D14), so no implicit port exists here. *Newest wins:* every `begin` takes the next ticket, and `apply` runs the effect of the newest one, whether it compiled or failed. A compile that finishes after a newer `prepare` still answers its own caller with its real outcome (the port's contract) and a success still fills the cache, but it never becomes the effect `apply` runs and never releases a caller waiting for the newer one; a cache hit settles at once, overtakes a compile still running and releases the callers that waited on it. The state suite proves these rules through the port with the completions written down in either order, and mutations of the ticket check, the cache write and the waiter release (by a compile and by a cache hit) turn it red. The Repository suite proves what the Repository decides over the real state: which port each call goes through, what it maps and logs, that a `prepare` which overtakes an `apply`'s own compile answers that `apply` without waiting for the compile, and that it resolves no executor (a mutation that does turns it red). *The bundled default:* while nothing has been prepared (the effects menu prepares the chosen effect as soon as its run has listed the catalog) the first `admit` hands back `BundledEffects.defaultEffect` (asked of the Repository through a closure, only then) to be compiled; the pipeline never learns the effect exists. An `apply` that meets the newest compile still running waits for it (one slow pass, during which the pipeline's in-flight cap drops ticks as `.inFlightCapReached`) rather than answering a failure the stats would count. An `apply` that compiles an effect itself starts that compile on the `WorkRunner` and waits for the *selection*, not for its own compile: when a newer `prepare` settles first, the frame goes on with the newer effect instead of waiting out a stale compile (and holding the in-flight cap for it), and the late compile still fills the cache and the log. The compile holds no lease, so the leases stay the caller's until `apply` returns. *Two kinds of failed compile.* A source that does not compile is the effect's fault: `.compileFailed`, final for the frames after it, which answer at once without compiling again, so a broken effect costs one compile and the pipeline passes every frame through. A compile that found no GPU context, or whose compiler service failed (`ShaderDiagnostics.cause == .environment`), is the runtime's: `.internalError`, as the renderer answers for the same cause, which keeps a good effect from being counted as a broken one, and not final — the selection remembers the effect and the next `apply` compiles it again, as the next pass asks for the render context again. Those retries run at the camera's pace, so the state counts a streak of them and the Repository logs only its first failure and the recovery ("compiled after N failed attempts"), the pipeline's rule for drop reasons: a change is news, a repeat is counted. `ShaderCompilationDataSource` marks the missing context as `.environment` itself and classifies the compiler's own errors by their raw code, with the pure `LibraryErrorMapping` (epic #42, D7): `MTLLibraryError.internal`, a transient fault of the Metal compiler service, is `.environment` too, and every other code, the `0` of a missing entry point included, is `.source`. A thin Gateway does not classify, so `ShaderLibraryGateway` returns the raw code and nothing else; the number is spelled out because nothing above the Gateway imports Metal, and `LibraryErrorCodeTests` pins it to the SDK the way `GPUCompletionMapping`'s codes are pinned. Classifying only the compiler's answer keeps a missing context `.environment` whatever its own code would read as. It matters once `prepare` is called by the effects menu's hot reload: a compiler service fault in the middle of an edit is retried by the next `apply` instead of being final, while a source that does not compile stays final. *The bundled effect is a string constant (D1):* `BundledEffectDataSource` holds `ChromaticGrainEffect`'s MSL in Swift and returns it as an `EffectSource`, so there is no `Bundle.main`, no bundle port and no resource bundle in the Xcode shell; `.lens` packages come from `EffectPackageDataSource` (#45) behind the same `EffectSource`, so the runtime's contract does not change. The effect drifts red and blue sideways by 1 to 4 pixels (the prelude's `noise` over 64-pixel bands and over `time` at half speed, sampled with a linear blend so the drift has no steps) and adds a per-frame grain (`hash` of the pixel and `frameIndex`); `MetalGateway smoke` compares one pass with its Swift twin (`ChromaticGrainReference`) under the GPU suites' one tolerance, directly and through the runtime over the live DataSources. *Uniforms* (`EffectUniforms.pass`, pure, built by the state when it admits the frame): `time` is seconds since the session's first frame as a `Float` (`EffectSession`: a session starts at frame index 0, which the pipeline counts from again at every `start`, or at the first frame the runtime is handed; a frame stamped before its session's start is at 0), `frameIndex` is the caller's, `resolution` is the output surface's size in pixels, and `seed` is 0 until a `RandomSource` exists (D3, MVP-C). The pass's grid is the output size rounded up to whole 16 × 16 threadgroups (`DispatchGrid.covering`), so it can overshoot `resolution` and a kernel bounds-checks its `gid` against the texture, as the bundled kernel does.

The fakes that the DataSource and UseCase suites drive (`FakeGPUGateway`, `FakeShaderLibraryGateway`, `FakeTextureCacheGateway`, `FakeEffectRuntimeRepository`, `InMemoryPreviewSink`, `FakePreviewGateway`) complete manually and in any order, refuse foreign handles with the live gateways' errors and in the live gateways' order, and are themselves under contract test (`Tests/TestDoublesTests`), so a lenient fake cannot hide a bug the live gateway would raise. **The file gateways throw instead of branching, and are proven by smoke (epic #42, D2 / D4, #44).** The thin-live rule forbids `if` / `guard` / `var`, so each place an OS call can fail or answer an optional is settled by the call's own shape. `FileWatchGatewayImpl` opens its descriptor with `FileDescriptor.open(…, .eventOnly)` from the System module, which throws for a path that cannot be watched; lyra's gateway tests the raw `open` result and returns `nil`, a branch this live does not have, and the port promises the throw. `FileSystemGatewayImpl.isDirectory` reads `URL.resourceValues(forKeys: [.isDirectoryKey])` (the `FileManager` form needs an inout `var`) after `resolvingSymlinksInPath()`: the plain resource value is `false` for a symlink to a directory while `contentsOfDirectory` lists it, so a package linked into the effects folder would be listed but skipped. `AppDirectoriesProviderImpl` takes `URL.applicationSupportDirectory`, the location `FileManager.urls(for:in:)` returns first, because it is not optional: there is no force unwrap and no fallback for an empty result that cannot happen. Watching has two descriptors because neither sees every save (a directory descriptor misses an in-place write to a file inside it, a file descriptor dies on a rename), and the smoke suite pins both halves, plus the shrinking truncate that posts only an attribute event (`.attrib` is in the mask for it). The suites assert "at least one" event, never a count, because the OS coalesces; a negative ("a stopped watch stays silent", "a directory watch does not hear an in-place write") waits on a sentinel watch that does hear the same write before it asserts. Every suite that touches the disk runs in a UUID-named temporary directory that it removes.

**`.lens` packages: a folder, a manifest and one kernel (epic #42, D1 / D3).** A package is a directory `<id>.lens/` in the effects folder holding `manifest.json` and `effect.metal`; the id is the directory name without the suffix, so editing either file never changes who the effect is, and the menu shows the manifest's `name` (trimmed). *Alternatives not taken:* a single `.metal` file has nowhere to put a name or an author; a zip has to be unpacked, which defeats editing the shader in place and having it reload; a manifest that names its own shader file would make the watch set and the entry point open-ended for nothing, so the two file names are fixed, the entry point is `effect` and the compile options are the defaults. *The manifest* (`EffectManifestDecoding`, pure) requires `formatVersion` (the integer 1, probed on its own first, so a newer package is reported as `unsupportedFormatVersion` even when its other keys have a shape this build would reject; a `formatVersion` that is a number but not an integer is `manifestInvalid` naming the key, `1.5` as not an integer and a whole number beyond `Int` as out of range, where the JSON decoder alone reports both as text that is not JSON, without a key) and a `name` that is not empty after the trim, takes `author` and `description` as optional and ignores every other key, `parameters` included until MVP-C: forward compatibility is the reason `formatVersion` exists, not strictness. Its `manifestInvalid` messages are built from the decoder's coding path rather than its wording, so they do not change with the OS or the locale. *A package that cannot be used is listed, not dropped (D3):* `EffectPackageDataSourceImpl` answers `.broken(id, problem)` so the menu can show a disabled item with the reason. It always reads both files and reports the first problem in a fixed order (manifest missing, unreadable, invalid; then shader missing, unreadable), so one broken file neither hides the other from the watch set nor makes the answer depend on read order. A file is *missing* or *unreadable* by its `CocoaError` code, never by a message. `fileReadNoSuchFile` is the shape `InMemoryFileSystemGateway` raises and `FileSystemGatewayImplTests` pins for the live gateway; `fileNoSuchFile` is accepted as well, defensively, in case an API reports a vanished path with it, and only a scripted `failRead` in `EffectPackageDataSourceTests` raises it. Every other failure, a non-Cocoa error included, is unreadable. *What to watch:* the folder and every package directory (as directories: an editor's atomic save only shows there) and every file that exists, the shader of a package whose manifest is broken included (as files: an in-place overwrite shows nowhere else); a missing file is not named because it cannot be watched, but its directory is, so creating it is noticed and the next listing watches it. *Folder, order and ids:* the first listing and `openFolder()` make the folder, `package(_:)` never does; the gateway promises no order, so the DataSource sorts by id in plain string order (the Repository orders for display); and since the id of a package comes back from a persisted selection (#51) and is joined into a path, `package(_:)` answers `nil` without touching the file system for an id that is not a `.package` id or not a single path component. *Where the checks end:* the DataSource proves that a package's files are readable and well formed; whether the kernel compiles is the runtime's (`prepare` answers `.compileFailed`, which the menu shows), and `Examples/Ripple.lens` is held to the format by `ExamplePackagesTests` (read through this DataSource it is ready, with a kernel named `effect` and no `Uniforms` of its own), while that its kernel compiles is not asserted by any test: it is checked on a device, in the Lane 1 run of #52 (`.claude/rules/dev-verification.md`, the timed table's steps 2 to 4).

**Effect catalog: one listing per change, assembled in the Repository (epic #42, D3).** Owner: `EffectPackageRepository` (`EffectPackageRepositoryImpl`, a stateless struct); it resolves `effectPackages`, `effectWatch`, `bundledEffects` (DataSource ports) and the two logs, so it respects the Repository lane of the key-path table. *One round per change.* `catalog()` is eager: making the stream starts a task of its own, off the frame path (an unstructured `Task`, not the `WorkRunner`, whose business is the frame path's work), that runs a round and then another whenever the watch speaks. A round lists the folder (`packages()`), arms `effectWatch.changes(of: inventory.watchSet)`, shows the catalog and waits for the watch's first element. The watch is let go before the next listing and the next round arms the *new* inventory's set, never the old one, since a package that arrived or went away changes what there is to watch (D4: each package directory as a directory for an editor's atomic rename, its manifest and shader as files for an in-place overwrite). The watch is armed before the catalog is shown, so the first change after any catalog a consumer has seen is heard. A re-listing is not covered: the old watch is let go before the folder is read again and the new one is armed only after that read, so an edit that lands after its file was read and before the new watch is armed is heard only with the change after it (the contract of `EffectWatch` arms everything before `changes(of:)` returns, but the set to arm comes from the listing, so listing and arming cannot be one step; the burst fold keeps the window to the few milliseconds of one listing, and the next save repairs it). The order of arming and showing is two adjacent statements, which a consumer on another thread cannot observe, so the suite pins it by sequence instead: thin wrappers around the two fakes write each call the Repository makes (listing the folder, arming a watch, and how many watches are still armed at that moment) to the developer log, between the "catalog listed" lines the Repository writes right before it shows a catalog, and the test reads back list, arm, shown, and after a change list, arm, shown again with no watch armed at either call. Ending the stream cancels the task, which lets go of the watch it armed (the end of a stream is the cleanup signal); a watch that ends *on its own*, which its contract never does, ends the catalog and logs an error instead of being listened to in a loop, so a catalog that has stopped being kept current is not mistaken for one that is. Whichever side ended it, the task records a developer-log line saying the catalog ended: the one signal that its work is done, which the ending tests wait for before they read the logs. *Every element is a listing, and every listing is shown.* The Repository does not compare a catalog with the one before: folding a burst into one element is `EffectWatchDataSource`'s (a 200 ms quiet period on `\.continuousClock`), and a listing that looks the same can be a package whose `effect.metal` changed, which `EffectCatalogUseCase` finds out by reading `source(of:)` again. That is why `source(of:)` reads afresh on every call and caches nothing (D5: the comparison for a hot reload is between two reads). *Why the Repository decides the order and the bundled entry.* A DataSource knows one kind of source (the folder, the bundled effect) and promises no order; the catalog is the join of two of them plus a presentation rule, which is orchestration, and the UseCase above must see `[EffectCatalogEntry]` without knowing that there are two sources, a folder or a watch. The bundled effect is always first (D3: the fallback must exist and be findable); the packages follow by display name, compared case-insensitively with numeric runs as numbers (`Effect 2` before `Effect 10`), the folder name as the tie-break, and no locale, so the menu reads the same on every machine; a broken package is listed under its folder name, since its manifest cannot be trusted for one, as `.broken(problem)` among the others. *`source(of:)`* answers `BundledEffects.defaultEffect` for the bundled effect's id and `.sourceMissing` for any other bundled id; a package is read once with `EffectPackages.package(_:)`: `.ready` is `.success(source)`, `.broken` is `.failure(problem)`, and nothing at all (the folder is gone) is `.failure(.manifestMissing)`, the first thing a package lacks. `openEffectsFolder()` is `EffectPackages.openFolder()`. The suite is `Tests/EffectPackageRepositoryTests` over `FakeEffectPackages` and `FakeEffectWatch`: the first catalog needs no `fire()`, a re-listing is a `fire()` after `packages.script(_:)`, the old watch's end is `terminations`, and every wait is `Collector.waitForCount`.

**Hot reload, the watch half: a directory watch on the folder and on each package, a file watch on each file, one element per burst (epic #42, D4, #46).** Owner: `EffectWatchDataSourceImpl` (a struct; port `EffectWatch`), which resolves `fileWatchGateway`, `continuousClock` and `developerLog` and nothing else, the DataSource lane of the key-path table. It decides nothing about *what* to watch: the set comes from the listing (`EffectPackageDataSource`, #45) and arming again after every listing is the Repository's (#47). *Two kinds of watch, one descriptor each.* An editor's atomic save replaces a directory entry, which a file descriptor never sees (it dies on the rename), and an in-place overwrite changes no entry, which a directory descriptor never sees. So the set carries the effects folder and each package folder as directories (`watch(directory:)`) and each package's manifest and shader as files (`watch(file:)`): what the DataSource arms is the folder's directory watch and, per package, its directory watch and a file watch for each of its files. A path that is both is armed twice and heard twice, and still makes one burst. *Armed before the call returns.* `changes(of:)` arms every directory and then every file before it hands the stream back, so the watches are live when the call is over: the first change after a catalog the Repository has shown is buffered until someone iterates instead of lost. *An un-armable path is logged and skipped.* A path that was in the listing and is gone by the time it is armed makes the gateway throw; the DataSource records it in the developer log (`.effect`) and goes on with the rest, because a throw would cost every other watch of the set. The skip costs only that path's watch: nothing arms it again and nothing asks for a listing because of it, so the listing stays as it was until some other armed watch hears an event. *One element per burst.* Whichever watch fires restarts the same quiet period, 200 ms (`quietPeriod`) on `\.continuousClock`. Each event gets a number and a `clock.sleep` of its own, a child of a `withDiscardingTaskGroup`; when a sleep ends it reports its number, and only the report of the newest event yields an element, so a period that a later event replaced yields nothing. The watches' callbacks run on any thread and only post `.changed` to a stream of signals; one task reads that stream, together with the sleeps' reports, in order, so the counter is touched by that task alone and needs no lock. The task is the DataSource's own unstructured `Task`, as in `ExtensionInstallDataSource`: this is off the frame path, which is the `WorkRunner`'s business. *The stream never ends on its own, and its end stops every watch exactly once.* Not for an empty set and not when nothing could be armed, because `EffectPackageRepository` reads an end it did not cause as the watch being gone and ends the catalog. Only the consumer ends it (its task is cancelled, it leaves the loop, or it drops the stream), and `onTermination` then stops every armed handle once, finishes the signals and cancels the task, which cancels the sleeps still parked: the period in progress is dropped, and an event after that reaches nobody. The live handle cannot see a double stop (cancelling a cancelled `DispatchSource` does nothing), so `FakeFileWatchGateway` counts it (`isBalanced`). *Why a DataSource and not a Gateway.* `FileWatchGateway` is a thin pass-through (no branch, no timing, no loop: `scripts/check-live-thin.sh`), whereas a quiet period is time plus a decision (restart or yield) that needs a test; one layer up the clock is injected and the kernel is `FakeFileWatchGateway`. *Testing.* The suite is `Tests/EffectWatchDataSourceTests` over `FakeFileWatchGateway` and a `GatedClock`: `gateway.fire(path)` is the file system and `clock.advance(by:)` is time. A `TestClock` would not do, because an event travels from the callback through the signals stream to a sleep and nothing observable says the sleep is parked, so an `advance` made too early is lost; `GatedClock.sleepers` fires once a sleep is registered, so a test advances only when the subject is waiting on it, and `parkedCount` shows a period running out (or not) without a window of ticks. The property test replays seeded gaps drawn around the boundary (0 to 600 ms, with 199, 200 and 201 among them) against a model that writes 200 ms out itself instead of reading `quietPeriod`, so changing the constant turns it red. *Alternative not taken: FSEvents.* It is recursive (one registration for the whole folder instead of a directory watch on the folder and on each package and a file watch on each file), but it is a C API with a run loop that does not fit the thin-live rule, and its coalescing latency is the OS's, not ours to step in a test; the two-watch `DispatchSource` shape is the one lyra already proves.

**The chosen effect is kept as one string in the user's defaults (epic #42, D6).** Chain: `SettingsRepositoryImpl` → `PreferencesDataStoreImpl` → `KeyValueStoreGatewayImpl`. *Why a DataStore.* The key and the string form are persistence-shaped knowledge, neither a Gateway's thin pass-through nor a DataSource's work against a changing world, so `Preferences` is the first port under `Domain/DataStore/`; the implementation resolves `keyValueStoreGateway` and `developerLog` and nothing else (the key-path lane of a `*DataStore`). *The form.* An `EffectID` is stored as `<origin>:<key>` (`package:glitch`, `bundled:Chromatic Grain`) under the role-named key `selectedEffect`. Both are persisted, so neither is renamed, and the suite pins them literally, because a symmetric rename of encoder and decoder would still round-trip. `StoredEffectID` is the pure conversion. It cuts at the first colon (an origin never contains one, a key may) and by Unicode scalar: cut by `Character`, a key that starts with a combining mark fuses with the colon before it and no longer decodes, which the seeded round-trip property test catches. Every `EffectID` round-trips, and a string that decodes encodes back to itself. An empty key is well-formed (it cannot name a catalog entry, so the fallback of D6 covers it). *A stored string that does not decode* (no colon, an unknown or differently cased origin, a value another build wrote) is not an error: `Preferences.selectedEffect()` answers `nil`, the DataStore writes one developer-log line under `.effect` and leaves the value where it is, since a newer build may read it again, and the next choice overwrites it. Reading never writes. A relaunch then starts from the bundled default, the fallback D6 specifies for a selection the catalog does not list (`EffectCatalogUseCase`, #48). *Layers.* `SettingsRepositoryImpl` is a pass-through to `Preferences`, kept for the chain (`ExtensionInstallRepository`'s reason); there is no `SettingsUseCase` until a settings UI exists. *The live gateway.* `UserDefaultsGateway` is registered in `HostDependencyInjection` only. `KeyValueStoreGatewayImpl(defaults:)` takes `.standard` in the app and a UUID-named suite in the smoke, which removes the suite's persistent domain after every test. The empty `<uuid>.plist` that emptying a domain makes the OS write at process exit is out of the test's reach (a delete from the test comes back), so the smoke shares one name per run, serialized, and leaves one such file per run instead of one per test. Its smoke runs anywhere, so the module is covered and absent from `codecov.yml`'s ignore list, and the thin-live lint, which reads that list, does not look at it; it is thin all the same. The port says `removeValue(forKey:)`, which `UserDefaults` calls `removeObject`. `scripts/check-physical-symbols.sh` rejects the name `UserDefaults` in every module but `UserDefaultsGateway`, in any spelling (`UserDefaults.standard`, a call or `.init`, a type annotation, a qualified `Foundation.UserDefaults`); a comment or a string literal is not code and does not count.

**Effect catalog: the UseCase selects and reloads; the pipeline never learns (epic #42, D5 / D6 / D11).** Owner: `EffectCatalogUseCase` (`EffectCatalogUseCaseImpl`), the only caller of `EffectRuntimeRepository.prepare`. *Hot reload is `prepare` again.* The Repository lists the catalog again after every change (a new package, a gone one, an edited file), so an edit arrives as a listing: for the chosen effect the UseCase reads `source(of:)` and, when the `EffectSource` differs from the last one it handed the runtime, prepares it (the first listing of a run always differs). A source that does not compile is `.compileFailed` and the pipeline passes frames through, MVP-A's rule unchanged; fixing the file prepares it again and brings the effect back. *There is no last-good library to keep:* it would collide with the runtime's selection rule (the newest `prepare` decides, success or failure) and hide the failure, while the pass-through is the shortest signal to an author that the edit broke the effect. *Fallback and restore (D6).* A run starts by reading the persisted choice, and each listing settles it: kept when the listing has it ready, otherwise the first bundled entry — a first start, a package that went away, or one whose files are broken. The bundled effect is taken from the listing because `bundledEffects` is a DataSource port, which a UseCase does not resolve. A fallback is logged and is not written back: only `select` writes the settings, so the persisted choice stays the user's last explicit one and comes back at the next launch if its package has. A listing without a bundled entry has nothing to fall back on and publishes nothing. *One state, published whenever it changes.* A listing that needs a `prepare` publishes after the runtime has answered, with the outcome; one that needs none publishes at once, carrying what the last attempt has answered so far (the outcome is `nil` while that attempt is still out, or has not begun because a choice is made before its `prepare` is issued and an answer for the effect chosen before can arrive in between, so the menu can show the chosen row before its outcome); a state equal to the last one is not published, so a hot reload that works, which changes nothing the menu shows, publishes nothing (the next listing is what proves it landed). `select` of a broken or unknown id answers `.unavailable` and changes and calls nothing; choosing the chosen effect again prepares it again, which is the retry after a runtime `.internalError`. A chosen package that is listed ready but whose source cannot be read just then is chosen and remembered all the same, is logged, and shows `.unavailable(problem)` as the outcome (the `select` that met it answers the same); the runtime keeps what it has, and a `prepare` still out goes on, its answer kept behind the problem rather than dropped. The next listing that reads the source again brings the answer back: the runtime's own when it already has that very source (nothing is prepared again), a fresh `prepare` for a new one. A `select` overtaken while it was remembered or while it read its source (by another choice, the catalog losing the package, a newer read of the same effect's source, or a new run) answers `.unavailable(nil)` and prepares nothing; the same two guards, a run number and a read number, keep a listing's stale read from preparing over a newer one. *Newest wins is mirrored, not re-implemented.* The runtime keeps the effect of its newest `prepare`, so the menu must show the newest request's outcome. The decisions are in one actor, `EffectCatalogSession` — low-rate and off the frame path, so an actor is allowed, and nothing in it touches a surface. Its `generation` is bumped in the same actor turn that calls `prepare`, with no suspension between, so its order is the runtime's; an answer that comes back after a newer `prepare` still reaches its own caller but publishes nothing, which the suites prove by completing the runtime fake's prepares in both orders. Before issuing anything, each flow re-checks that the effect it read the source of is still the chosen one, so a `select` that arrives while a listing waits for a source (or the reverse) leaves the effect to the newest choice. *Observers.* `observe()` is synchronous in the port, which an actor cannot be, so the states go through a `CurrentValueSubject` (`EffectCatalogBroadcast`): a stream is subscribed while it is built, before `observe()` returns, so a state published right after is never missed, the current state arrives at once and any number of observers see the same sequence. The lock the UseCases are denied is the subject's own, and every `send` comes from the one actor. The subjects are never completed: a run that ends (its task cancelled) ends the streams opened so far, lets go of the catalog and forgets the state and the last-prepared source, so a later run restores the choice and prepares again. A stream opened in the very instant a run ends may be handed that run's last state or miss the end, because its two subscriptions and the run's two steps of ending are not one step and a lock is not available here; the port asks callers not to open one then, and the Interactor opens its stream as its run begins, after the run before has returned. *What it relies on:* `EffectPackageRepository.catalog()` listing again after every change, an identical entries array included, since a shader edit changes no row.

**The effects menu's Interactor and Presenter (epic #42, D9).** Owner: `EffectInteractorImpl` (`EffectInteractor`) and `MenuBarPresenter` (`Presenters`). The Interactor owns the one task that runs the catalog: `start()` runs `EffectCatalogUseCase.run()` and the forwarding of `observe()` into a `CurrentValueSubject` as the two children of one task, so cancelling the task reaches both, and `state` is that subject without its `nil` — empty before the first `start()`, the latest state for every later subscriber. `start()` and `stop()` are synchronous on the port, so each only queues a command on an `AsyncStream`; one supervising task, started when the Interactor is made, carries the commands out one at a time, in call order: it cancels the run that is alive, waits for it, and begins the next on `start`. That is how the task handle needs neither a lock (the physical-symbol lint bans `NSLock` and `OSAllocatedUnfairLock` above the Gateway) nor an actor hop that could reorder `start(); stop()` (an unstructured `Task { await actor.start() }` per call could); waiting for the old run before the new one begins is what keeps a stale state from landing after a fresh one. A second `start()` therefore restarts the catalog, as the port says, and a released Interactor ends the run it owned. `select(_:)` returns nothing on the port, so it spawns a task for the UseCase's answer and writes one log line (`DeveloperLog` for `.prepared`, `ErrorLog` for a failed or unavailable effect); the outcome reaches the menu through `state`. It is deliberately not one of the queued commands, and it does not wait for an earlier `select` either: the runtime's newest-wins (*Effect runtime* above) is built so that a newer `prepare` overtakes a slow compile, and a queue here would hold the newer choice back behind the older one's compile. The price is that two `select`s made in the same instant may reach the UseCase in either order, which a person choosing from a menu does not produce; the port documents it, and a caller that needs an order waits for the first outcome in `state`. `MenuBarPresenter` is `@MainActor`; a `sink` hands every state to an `AsyncStream` that keeps the newest (`bufferingNewest(1)`), and a main-actor task applies them. It is neither `receive(on: DispatchQueue.main)` (the physical-symbol lint bans the queue, and a test would have to poll for the hop) nor a task over `interactor.state.values`: an `AsyncPublisher` asks for one value at a time, and a state sent while the task is still applying the previous one is dropped (a producer on another thread sending 100,000 states at a main-actor consumer that did a little work for each saw fewer than 2,000 of them arrive), which could leave the menu on a state that is no longer the catalog's. The `sink` takes unlimited demand, and the stream keeps the last state until the task has applied it. `stop()` ends the observation by cancelling the subscription and the task and finishing the stream, and the loop checks the cancellation before it applies a state: an `AsyncStream` still delivers a value it had already handed to its consumer, so without the check a state sent just before `stop()` would change the rows after it. Its suite waits with `settle` on `$items` / `$status` alone. It owns the Interactor's lifecycle for the menu — `start()` observes and then starts the Interactor, `stop()` ends both, and a started Presenter that is let go does what `stop()` does (its observation task and the Interactor's run would otherwise outlive it) — because the Router above it resolves no Interactor and may not skip a layer; the Router decides when to call them, and nothing starts in `init`. The Presenter's `start()` / `stop()` are therefore the only calls that begin and end the menu: whoever wires it (the Router, which the host's and the dev harness's delegates start) calls them and never `effectInteractor.start()` itself, because a second `start()` is a restart, so the catalog's `run()` would run twice at launch and the first state would be sent twice. `scripts/check-dependency-keypaths.sh` keeps the entry points to it: `App` and `DevHarness` are denied `\.effectInteractor` (*Menu bar* below). Display data follows the layer rules: `EffectMenuItem` is pure data in `Entity`, the wording of a package problem or a failure (`"<name>: compile failed"`) is a pure function inside `Presenters`, and `EffectCatalogEntry` carries the manifest's `author` so that the Presenter can show it (the Repository that assembles the catalog fills it, #47). Alternatives not taken: an `actor` holding the task (reorders unless every call goes through a mailbox anyway, which is this design with an extra type), a lock-protected task slot (banned above the Gateway), and a Presenter that subscribes in `init` (a constructor with a side effect, and the Router could not choose when the catalog starts).

**Menu bar: one SwiftUI menu, shared with the harness (epic #42, D8).** Owner: `EffectMenu` (`Views`), `AppRouter`, and what starts the Router: `HostAppDelegate`, and `HarnessMenu` for the harness's delegate. *One declaration, two hosts.* `EffectMenu` is a SwiftUI `View` over a `MenuBarPresenter` whose content is only what a menu can show: a `Toggle` per `EffectMenuItem`, `Divider`s, a `Text` for the status line, `Button`s for *Browse Effects…*, *Open Effects Folder…* and *Quit*. The same declaration is the content of the host's `MenuBarExtra(.menu)` and, in the dev harness, of an `NSHostingMenu` in the main menu. The View maps values and decides nothing: the rows and their order, the checked row (`isSelected`), the disabled row (`isEnabled`), the second line (`detail`: the author, or why a package cannot be chosen) and the status line all come from the Presenter (`MenuBarText`), so no wording is repeated in the View. A row is a `Toggle`, not a `Button` with a checkmark image, because SwiftUI turns a toggle into a menu item whose `state` is `.on`: the mark sits in the state column and every title lines up. The toggle ignores the value it is flipped to: whatever it flips to, the user asked for this effect, and the Presenter's `isSelected` stays the only truth about what is checked (choosing the checked row asks for the effect that is already chosen). *Why not a hand-built `NSMenu`:* it would be a second description of the same rows in AppKit, with `NSMenuItem` targets and a diff on every state, in a file nothing tests, and the harness could not share it with a `MenuBarExtra`. `NSHostingMenu` is macOS 14.4+ while the package's floor is 14.0, so the harness adds its Effects item under `#available(macOS 14.4, *)`; the host's `MenuBarExtra` needs no guard. *Known limit on macOS 14: the second line.* A row's second `Text` becomes the `NSMenuItem`'s `subtitle`, which the SDK declares `API_AVAILABLE(macos(14.4))` and which, by the note in `NSMenuItem.h` (the same text in the macOS 26.4 and 26.5 SDKs), is not shown on macOS 14 for an item with an attributed title and is shown on macOS 15 and later. With the floor at 14.0, the rows of the host's `MenuBarExtra` may lack the second line there: the author of a package, and for one that cannot be chosen the reason it cannot (the row is still listed, disabled, and the logs carry the reason). The header does not say whether SwiftUI gives these rows an attributed title, and nothing here has run on macOS 14, so *may* is the claim; Lane 1 step 8 records what is drawn, with the OS version. Alternative not taken: folding the detail into the title (`Ripple — Example Author`), which would draw everywhere but give up the second line on the systems that do draw it, and put the author into the title the manifest's `name` owns. *The Router starts the Presenter, and nobody else does.* `AppRouter` (`@MainActor`) builds the one `MenuBarPresenter` in `init` through an injectable factory (the default builds the live one) and calls its `start()` / `stop()`. The Presenter owns the `EffectInteractor`'s lifecycle (*The effects menu's Interactor and Presenter* above) and the Interactor's live value is a process-wide `static let`, so exactly one owner may start it: the entry lane (`HostAppDelegate`; in the harness `HarnessMenu`, which the delegate calls) starts and stops the Router and never calls `effectInteractor`, because a second `start()` is a restart. That is checked, not left to review: the Entry lane may resolve Interactors (`cameraInteractor`, `harnessInteractor`), so the kind rule of `scripts/check-dependency-keypaths.sh` cannot say it, and the script holds a per-key denial instead: `App` and `DevHarness` may not resolve `\.effectInteractor`, and a denial whose key, module or reason has gone fails (`.claude/rules/architecture-boundaries.md` → *Per-key denials*). Alternative not taken: a placement check in the style of `scripts/check-live-owner.sh` (a grep for the key path in two files), which matches comments and strings as well as resolutions (a doc comment that names the key path trips it) and would sit apart from the lane table it amends. The Router resolves nothing (the key-path lint gives the View lane the Presenter and Support only), keeps no state beyond the Presenters and the picker's open window (*Effect picker* below), and adds nothing to the menu's Presenter's own guarantees (a second `start()` while started does nothing; a started Presenter that is let go stops). **Effect picker: a second view of the menu's state, opened by the Router (#12).** Owner: `EffectPickerPresenter` (`Presenters`), `EffectPickerView` (`Views`), and `AppRouter` with its `EffectPickerWindow`. *One state, two views.* The picker is a window with one cell per catalog entry, over the same `EffectInteractor.state` the menu draws: the chosen cell is the menu's checked row because both come from the one state's `selection`, not because one view tells the other, and a cell is enabled exactly when its row is. Choosing a cell is `EffectInteractor.select`, as choosing a row is. The wording is shared, not repeated: a cell's second line is the row's (`MenuBarText.detail(of:)`), the status line above the grid is the menu's (`MenuBarText.status(of:)`), and the hover help says the whole of what the cell abbreviates: the name with its author, or for a broken package `<name> cannot be chosen: <reason>`. *It only observes.* The menu's Presenter owns the Interactor's run (*The effects menu's Interactor and Presenter* above), and a second `start()` is a restart, so `EffectPickerPresenter.start()` subscribes to `state` and does nothing else, and `stop()` lets go of it and clears the search; `state` replays the latest value, so a picker opened late shows the catalog at once. A real image joins as a second case once the catalog carries one: the Presenter chooses between the two and the View draws the new case, and nothing else changes. *The Router opens and closes it.* `AppRouter` is the menu's `MenuBarRouting`: *Browse Effects…* goes from the View to `MenuBarPresenter.browseEffects()` and on to the Router, which the Presenter holds weak because the Router owns it. Alternatives not taken: a picker Presenter that starts the Interactor (the catalog would restart each time the window opens), a picker that reads the menu's Presenter (a Presenter depending on a Presenter, and no picker without the menu), and the geometry in `Views` (untested logic in a coverage-ignored module).

**IOSurface → `MTLTexture` by `makeTexture(descriptor:iosurface:plane:)`, not `CVMetalTextureCache`.** Frames are already IOSurfaces — there is no `CVPixelBuffer` to feed a texture cache — so `TextureCacheGateway.bind` wraps plane 0 directly: `bgra8Unorm`, `.shared` storage (the product targets Apple silicon only), `shaderRead | shaderWrite`. A thin live cannot branch on the device, so the storage mode is hardcoded; the #15 spike ran the same compute fill through `.shared` and `.managed` textures on Apple silicon, and the `test-gpu` job re-proves `.shared` on the runner's paravirtual device on every PR. The surface's rows must be 16-byte aligned or Metal aborts the process inside `makeTexture` (validation layer or not), and IOSurface keeps an explicit `bytesPerRow` exactly as given — `width * 4` for a 6-pixel-wide surface stays 24 — so the alignment belongs to allocation, not to binding: `IOSurfaceGateway.create` passes the request through `IOSurfaceAlignProperty` (one OS call, no branch, so the gateway stays thin) and every surface it makes is bindable, slate included. Aligning in `SurfacePoolDataSource` instead would need the alignment hardcoded above the OS boundary or a second port call every allocation path must remember (#32). Dispatch is `dispatchThreadgroups` only: whole threadgroups work on every family, `DispatchGrid.covering` rounds the grid up and every kernel bounds-checks its `gid`. The compile handle (`LibraryHandle`) is the entry kernel's `MTLComputePipelineState`, built once in `compile` and cached by `EffectRuntimeStateDataSource`, never per frame; the pass (`ComputePass`) carries handles, so it is declared in `Domain` next to them rather than in `Entity`.

**`fastMathEnabled`, not `mathMode`.** `ShaderCompileOptions.precise` is the port's vocabulary; the live sets `MTLCompileOptions.fastMathEnabled = !precise` and nothing else. `mathMode` needs macOS 15, and `languageVersion` / `#available` would be a branch in a thin live. The deployment target is 14, where `fastMathEnabled` is not yet deprecated, so the build stays warning-free.

**No Metal in the extension process.** `MetalGateway` and `MetalKitPreviewGateway` are linked by `HostDependencyInjection` only. `scripts/check-extension-no-metal.sh` (in `make check`) walks `swift package dump-package` from `ExtensionApp` and `ExtensionDependencyInjection` and fails when either reaches a Metal module, `PreviewDataSource` (it carries the preview kernel's MSL) or `Views` (it imports MetalKit).

**Preview: one compute blit into the view's layer.** The preview reuses the effect path's own vocabulary instead of adding a render pipeline: `PreviewDataSource` compiles one kernel (`previewBlit`: aspect-fit, bilinear, black bars, bounds-checked `gid`) through `ShaderLibraryGateway` into the same `LibraryHandle` (a compute pipeline state), and `PreviewGateway.draw` dispatches it with the frame's texture at index 0 and the drawable's texture at index 1. That needs `framebufferOnly = false` on the view, which `prepare` sets with the device, `bgra8Unorm`, and a paused draw loop (`isPaused`, no `setNeedsDisplay`): frames, not the display link, drive the preview. A paused `MTKView` stops sizing its layer — it updates its own `drawableSize` on a resize or a scale change, but the layer keeps the size of its first drawable — so `prepare` also sets the view's delegate to a forwarder that copies every `drawableSizeWillChange` onto the layer; the layer handle holds the forwarder (the view holds its delegate weakly), and `PreviewSmokeTests` resizes a view between two draws to pin it. The drawable comes from `CAMetalLayer.nextDrawable()`, not `MTKView.currentDrawable` — the latter is cached until the view's own `draw` and is a main-thread API, while `nextDrawable` may be called from the frame executor. Readying the view is main-thread work, so `attach` is `@MainActor` all the way down (`PreviewSink`, `PreviewRenderer`, `PreviewGateway.prepare`); `attach` makes a GPU context, readies the view and then hands the layer to the frame executor, where it compiles the kernel once per attach — never per frame. A failed compile detaches (frames complete at once) and is logged; a refused attach leaves the previous view attached. One draw is in flight at a time and the latest frame wins: a frame that arrives while a draw is pending replaces the waiting one, and the replaced frame completes at once, so every presented frame completes exactly once and the pipeline's in-flight cap is never held by the preview. GPU errors are logged under `LogSubsystem.preview` and the frame still completes. Trade-off: `nextDrawable` can block up to one second on the frame executor when the compositor holds every drawable (e.g. an occluded window); measuring that on a device is Lane 1's job, and moving the wait off the executor is the fallback. The harness makes it observable: the pipeline's ticks share the executor, so its once-a-second `pipeline` summary line drifts apart in `log stream` timestamps while a draw blocks (`.claude/rules/dev-verification.md` Lane 1).

**Dev harness: a SwiftPM executable with a linked-in `Info.plist`.** `swift run dev-harness` needs a camera usage string and a stable bundle identifier for TCC, but an SPM executable has no bundle, so `Tools/DevHarness/Info.plist` is linked into the binary as its `__TEXT,__info_plist` section (`linkerSettings: .unsafeFlags(["-Xlinker", "-sectcreate", …])`, with an absolute path from `Context.packageDirectory` so the link does not depend on the working directory). It is the one hand-written plist: the "never hand-written" rule is about the xcodegen shells, whose plists carry the product's bundle IDs and come from `project.yml`; xcodegen never builds this executable, and the plist is role-named (`com.generald.dev-harness`) and scanned by the product-name lint like `Sources/`. `unsafeFlags` is accepted only in a root package, which this always is when built (the Xcode shell links only the `App` and `ExtensionApp` products, neither of which contains `DevHarness`). Linker settings follow the target into every product that links it, so the section also lands in the `swift test` bundle (which `DevHarnessTests` links), where no main bundle reads it. SwiftPM does not track the plist as a link input (only a linker flag names it), so an edit to it alone does not relink: `make build-dev-harness` deletes the binary before building, and a plain `swift build` / `swift run` after a plist-only edit keeps the old section. Whether TCC keys the prompt to the harness's bundle ID or to the terminal that started it (the "responsible process") is a device question; the fallback — granting the terminal app — is in Lane 1. Alternative not taken: an xcodegen `Harness` app target, which would add a dev-only target to `project.yml` and leave `swift run` without a camera prompt. The usage string says what the harness does: it shows the camera video with an effect in its own window, and the frames stay there. The harness keeps the layer chain like the host app: `HarnessSession` resolves only `HarnessInteractor`, which drives `CameraControlUseCase` and `FramePipelineUseCase`; the session has no Presenter, because the harness has no display state beyond the preview itself (the host app's entry lane resolves `CameraInteractor` the same way). The Effects menu in the harness's main menu is the exception that does not touch the session: the host's `EffectMenu` in an `NSHostingMenu`, over the `MenuBarPresenter` of an `AppRouter` that `HarnessMenu` owns (*Menu bar* below), so the effect switch and the hot reload can be tried here without the extension. It runs the host's real graph (the camera, the pipeline, the real effect runtime over the live GPU gateways, the real preview) with one substitution, the virtual camera sink, which is the next decision.

**Dev harness sink: discard, substituted at construction (epic #14, D13).** The harness has no extension to send to, so the real sink would answer `.dropped(.notConnected)` for every frame and the summary's `dropped` would say nothing. `DiscardingVirtualCameraSink` (in `VirtualCameraRepository`, a covered module; a dependency-free `Sendable` struct) accepts every frame: `connect` succeeds, `send` is `.sent`, `observe` never reports. It exists for the harness only, and the host app keeps `VirtualCameraRepositoryImpl`. It is the production-side twin of `FakeVirtualCameraSink`: `Sources` may not use `TestDoubles`, and the fake's scripted outcomes are not wanted at runtime. The substitution is `HostDependencyInjection`'s `DependencyValues.useDiscardingVirtualCameraSink()` (the DI targets are the only importers of implementation modules, so `DevHarness` cannot name the type), applied by `HarnessSession.live()` around the *construction* of the session: `@Dependency` captures the current `DependencyValues` when the property wrapper is initialised, and swift-dependencies caches a live value globally on its first resolution, so the interactor and the pipeline under it must be built inside the scope; a `withDependencies` around `start()` later cannot be relied on, because whichever of `attach` and `start` resolves them first fixes the sink for good. `HarnessWiringTests` builds the real interactor and pipeline by hand in that scope with the sink left unimplemented behind it (it does not call `live()`). `HarnessLiveWiringTests` is the one test that does: `HarnessSession.live()` under `context = .live`, fakes only at the OS boundary, and a Mach look-up count of 0, so a `live()` that stopped applying the substitution, or applied it outside the construction, leaves the real sink waiting for an extension and the test red. It is exactly one test because the live registrations are process-wide `static let`s that keep the first builder's scope (its header says so), and it is also the one suite that resolves `effectInteractor` and `effectCatalogUseCase` live (*The effect catalog follows the same rule* above). `scripts/check-dev-substitutions.sh` (in `make check`) keeps the pieces in place: the sink and its helper are named only by `HarnessSession.swift`, `DevelopmentSubstitutions.swift` and `VirtualCameraRepository`, and the app delegate builds its session with `live()`; `scripts/check-live-thin.sh` holds the helper to one assignment per member. The device shows the same thing in Lane 1 (`frames` rising with `received` rather than `dropped`). Alternatives not taken: a flag or a no-op mode in `VirtualCameraRepositoryImpl` (a development case branching inside production code); `prepareDependencies` at process start (a global mutation that also reaches the test bundle that links `DevHarness`); a fourth DI target for one line.

**Untrusted shaders: contain, detect, disable.** A community shader cannot run CPU code but can hang the GPU (`timeout`), fault (`pageFault`) and, repeated, get the process's Metal access revoked (`accessRevoked`); Metal offers no execution-time limit or abort. Policy (pure, in `EffectHealthPolicy`): one command buffer per effect, `errorOptions = .encoderExecutionStatus` to attribute faults, pass-through on failure, `gpuStart/gpuEnd` budget, auto-disable after k consecutive failures with a cool-down, disabled set persisted. Tests synthesize raw error codes; real hangs are a manual VM lane only.

**One effect, one command buffer; the outcome is interpreted once (epic #14, D4).** `GPURenderDataSource` is where a GPU outcome gets its meaning. Each `render` hops onto the `FrameExecutor` first, because the surface pool it resolves the two leases through is confined there; a lease that no longer resolves is `.invalidResource` before any gateway is asked for anything (no context, no binding, no command buffer). It then binds input (texture 0) and output (texture 1), commits exactly one `ComputePass` over a grid covering the output surface, and maps the completion with the pure `GPUCompletionMapping`. Failures before the commit split by cause: a surface that cannot be bound is `.invalidResource`, a GPU runtime that cannot take the pass (no context, no encoder, a foreign library handle) is `.internalError`, and both are logged because the mapping drops the gateway's error. A raw code counts only in `MTLCommandBufferErrorDomain` — the same number from another domain is `unknown(code:)`, never misread as a timeout. Every texture bound for a pass is unbound exactly once on every path: at once when a later bind or the encode fails, otherwise from the command buffer's completion, so the bindings live exactly as long as the GPU reads the surfaces; `FakeTextureCacheGateway.isBalanced` proves it under any completion order (a 50-seed property test). The GPU context is made on the first pass and kept; a failed `makeContext` is not remembered, so a later pass asks again. A caller's cancellation does not cut a pass short — a committed command buffer cannot be withdrawn, so the caller waits for its completion, keeps both leases until `render` returns (the renderer never releases one), and the textures still go back; the `GPURenderer` port states this, and `FakeGPURenderer` behaves the same so a Repository suite cannot be written against a cancelled render that returns early. The DataSource keeps no failure history: per-frame pass-through is the pipeline's (#22), and counting, budget and auto-disable are `EffectHealthPolicy`'s (MVP-D). **No uniform byte packer:** `MetalGateway` hands `EffectUniforms` itself to `setBytes` with its stride, so the packing is the struct's memory; a seeded property test reads the bytes a pass carries at the MSL offsets (0 / 4 / 8 / 12 / 16, stride 24) for arbitrary bit patterns instead of maintaining a second, parallel encoding.

**Foundation allowed in Entity/Domain.** lyra's "Domain has no Foundation" rule is not carried over — lyra itself imports Foundation in nine Domain files, and the line worth defending is OS frameworks, which the lint enforces instead.

**Three DI targets.** The extension must not link host-only implementations (Metal, AVFoundation, SwiftUI). `CommonDependencyInjection` registers what both processes share (surface pool, Mach, log, host time); `HostDependencyInjection` and `ExtensionDependencyInjection` add the rest. One wiring point per process preserves lyra's "single registration site" intent.

**Shared `TestDoubles` target.** Gateway fakes are used by DataSource, UseCase and integration suites; duplicating them per suite drifts. Doubles used by one suite stay private to it. No test implementation lives in production targets (decoy's `InMemory*` live modules are not copied).

**Seeded property tests via `@Test(arguments:)`.** No external PBT library. `forAll(seeds:)` runs its body over `standardSeeds` (0..<32); `Seeds.range(0..<N)` (in `Tests/TestSupport`) names a wider or different seed set for `@Test(arguments:)`, so each seed is a separate, parallel test case; nightly widens the range. Targets: parameter clamping, uniform layout alignment (the bytes a pass hands to `setBytes` against the MSL `Uniforms` offsets), bind/unbind balance and answer attribution under any completion order, manifest encode/decode round-trip, the stored form of an `EffectID` (`StoredEffectID`), hash-noise determinism and range, source assembly line mapping, health state machine monotonicity, surface pool invariants, PTS monotonicity (including the relay's slate/real interleaving), debounce coalescing (`EffectWatchDataSourceImpl`: one element per burst over gaps that straddle the quiet period), preview exactly-once completion with latest-wins and one draw in flight, the effect picker's grid (`EffectPickerGeometry`: the most columns of the minimum width that fit between the insets, from 1 to 32, and cells and gaps that fill the row), and the pipeline's leases under any order of effect answer, send, preview completion and stop.

**Mach receive loop lives in the DataSource; host death has two detectors.** decoy's blocking `while mach_msg` loop inside the gateway would violate the thin-live rule and saturate the cooperative pool. `MachMessageGateway.receive(on:)` returns one `IncomingMessage` (async, cancellable by destroying the receive right) and `FrameReceiverDataSource` owns the loop. The wire has three message shapes: a frame (`msgh_id` 0x10001), the host's *hello* (0x10002, carries the host's presence send right) and the kernel's dead-name notification (`msgh_id` 72, accepted only at its fixed 36-byte size and non-complex); the kernel's port-deleted (65) and send-once (71) notices, accepted only at their fixed sizes and non-complex, decode to `.notice` and are ignored; anything else is `.malformedMessage`. **Primary detector, frame gap:** a watchdog on `\.continuousClock` wakes every `frameGap / 4` (default gap 2 s), so a host that is stopped, hung or killed without the kernel noticing is declared lost within 1.25 × `frameGap`. The gap is counted from the last frame, or from the moment the receiver starts listening while no host has been seen yet (`awaitingFirstHost`, cleared by the first frame or any loss; a hello only restarts the count, since a host that greets and then never sends is still absent), so a host that never launches is declared lost once, with `hostLost(.frameGap)`, and the relay enters the slate instead of leaving the client with no frames; `hostConnected` still fires on the first frame after start and after every loss. **Secondary detector, dead-name:** after look-up the host allocates a presence receive right, announces the send right in a hello and keeps the receive right; the extension requests a dead-name notification for the right it received, delivered to its own service port, so the notification arrives through the same receive loop. A dead-name counts only when the name matches the right currently held (a stale or foreign name is ignored); a new hello deallocates the previous right (a replacing host), which makes the kernel send a port-deleted notice (`.notice`); the matching dead name is released with `releaseDeadName` (`mach_port_get_refs` + `mach_port_mod_refs`; `mach_port_destroy` is deprecated) because the notification adds a user reference of its own; a failed notification request is logged, the right deallocated and no event raised. An explicit disconnect and `destinationLost` release the presence receive right on the host and reach the extension as a dead name. A replacing connect does not raise `hostLost`: the new hello is sent before the old right is given up, so the extension adopts it first and then ignores the old name. Either detector yields `hostLost`; hello and dead-name never end the loop, but `hostLost(.receiveFailed)` does (the run ends and relaunching is the caller's job). A full destination queue is not a loss: `MACH_SEND_TIMED_OUT` becomes `MachError.queueFull`, the frame is dropped as `.queueFull` and the link is kept. **Not yet measured on a device (issue #3):** `kill -9` of the host is expected to fire dead-name first (the kernel destroys the presence receive right at once) with the frame gap as backstop; `kill -STOP` leaves the right alive, so only the frame gap can fire; `kill -CONT` resumes frames and the relay leaves the slate on the first newer real frame. The recipe is in `.claude/rules/dev-verification.md`.

**Host absence and slate.** Owner: `ExtensionRelayUseCase`, with the pure value type `SlateSchedule` (`live(lastEmitted)` / `slate(base, next, lastEmitted)`). On *any* `hostLost` the relay enters the slate regardless of whether a client is currently streaming — a deliberate simplification: nothing has to be re-evaluated on `streamStarted`, and a client that opens during the slate sees black at once; frames that find no client count in `framesDropped`. The slate PTS base is `max(hostTime.now(), lastEmitted + frameDuration)`, never behind the last real PTS, and slate frame *n* is stamped `base + n × (1/fps)` (`FrameRate.slateTime`). One black surface is allocated per slate episode (`surfaceRepository.allocate(descriptor, filledWith: 0)`), reused by every tick of the episode and released when it ends; if the allocation fails the relay logs an error, starts no scheduler and retries on the next `hostLost`. `FrameScheduler` ticks send the slate frames (`stats.slateFrames`, shown as `slate=<n>` in the one-line summary). The first real frame ends the slate: scheduler stopped, slate token released, the frame relayed. **Real PTS is re-based, not dropped:** slate PTS follows wall-clock time while a real frame carries its capture time (older by the camera latency), so a real PTS can sit below the last slate PTS for good. The resuming frame therefore sets `shift = lastEmitted + 1 ns − pts` (0 when it is already ahead) and every real frame is relayed at `pts + shift` until the next episode recomputes it; the stream's PTS stays strictly increasing and a laggy camera recovers. Only a frame whose shifted PTS does not advance is dropped as `.nonMonotonic`. When `run` ends, `defer` stops the scheduler and releases everything, so `liveCount == 0`.

**Host reconnect.** Owner: `FramePipelineUseCase` (a UseCase-owned task, not the transport). `destinationLost` starts one reconnect through the `WorkRunner` port (the frame path never starts an unstructured `Task` itself; state transitions stay on the `FrameExecutor`, the port owns only the async work's lifetime and hands back a `WorkHandle`). That work calls `virtualCameraSink.connect()` (its retry policy sleeps on `\.continuousClock`). `PipelinePhase` (`idle, connecting, connected, disconnected, reconnecting, stopped`; implementation-only, a `CurrentValueSubject`) makes the state testable. A loss that arrives while connecting or reconnecting is remembered and replayed after the attempt settles; repeated losses without a `.sent` in between back off with `RetryPolicy.serviceLookup` delays (250 ms doubling to 5 s), so a flapping extension is not hammered. An explicit disconnect or a `lookupFailed` never reconnects, and `stop()` cancels the work through its handle, which ends a back-off sleep with `CancellationError` so a later clock advance never reconnects. When a connect replaces a live link, the transport announces the new presence right *before* it gives back the old port and presence; a failed announce is logged and the link stays up.

**Install transitions.** The `SystemExtensionGateway` delegate yields raw events with no interpretation (`.failed(code:description:)`, `.willReplaceExisting`, and it always answers `.replace`); `ExtensionInstallDataSource` maps `OSSystemExtensionError` codes in one pure function: 10 (forbidden by system policy) → `denied`; 11, 12 (request canceled / superseded) → `canceled`; 2–9 (missing entitlement, unsupported parent bundle location, extension not found, extension missing identifier, duplicate extension identifier, unknown extension category, invalid code signature, validation failed) → `invalidBuild(code:)`; anything else → `other(code:description:)`. `.willReplaceExisting` re-yields `installing` only while installing (during `needsApproval` it is only logged). A stream that ends without a result is `failed(.other(code: -1, …))`. A generation counter on `drive()` keeps the events of a superseded request (after `retryAfterFailure`) from touching the new one.

**Service-name triple.** The Mach service name is declared once in `ProductIdentity`; host entitlements (`mach-lookup`), extension entitlements (`mach-register`) and the constant must agree or `bootstrap_look_up` fails silently (decoy). `scripts/check-service-names.sh` (in `make check`) compares the three.

**Thin shells, thin lives.** `Apps/**` holds only `main.swift` and assets, plus the generated `Info.plist` / entitlements (`scripts/check-shell-thin.sh` bounds line counts and file kinds). Coverage-ignored Gateway modules obey decoy's thin-live rule: ≤ 50 lines per file, no `if`/`guard`/`switch`/`for`, no `var` (`scripts/check-live-thin.sh`), and so does the one coverage-ignored file outside a Gateway that is not plain wiring, `DevelopmentSubstitutions.swift` in `HostDependencyInjection`. `FileSystemGateway`, `FileWatchGateway` and `AppDirectories` run in the coverage run (their smoke suites are real), so the script does not police them; they are written to the same rule by hand.

**Coverage.** codecov as lyra (`project: auto / 1%`, `patch: 80%`). Ignored: `Domain`, the three DI targets, `Views`, `Apps/**`, and the Gateway modules whose real backend is not exercised in the coverage run — `MachGateway`, `SystemExtensionGateway`, `CMIOExtensionGateway`, `AVFoundationGateway` (no extension, camera or CMIO on a runner), `WorkspaceGateway` (opening Finder is a side effect nothing on a runner can observe) and `MetalGateway`, `MetalKitPreviewGateway` (GPU suites run in their own process and never feed codecov, even though the runner has a Metal device) — fixed, never environment-conditional. GPU suites run in `make test-gpu` outside coverage. `DevHarness` is covered, like `App`: `HarnessSession` runs under `DevHarnessTests` (its behaviour is `HarnessInteractor`'s and `FramePipelineUseCase`'s, each with its own suite, and `HarnessWiringTests` runs the pair over fakes), and `HarnessMenu` (the main menu, and the Router's start and stop) runs under it too; the AppKit glue around them (`main.swift`, `HarnessAppDelegate`) stays a few untested lines.

**Decoy lessons carried as ADRs.** (1) IOSurface across actor boundaries crashes on Swift 6.3 → leases + no actors. (2) Service-name triple → lint. (3) `CMIOExtensionStream` needs `.hostTime` clock and real mach-uptime PTS. (4) `needsApproval` must be surfaced in UI with a Settings deep link; the app must sit under `/Applications` for activation. (5) Two Developer ID provisioning profiles are required; the release workflow had never run end-to-end in decoy.

**The extension's entry point resolves the relay UseCase.** The Interactor, Presenter and View lanes exist for the GUI (the ADR above); the extension process has no GUI, so it has none of them, and `ExtensionDependencyInjection` registers the relay UseCase and the layers beneath it only. `ExtensionApp` therefore resolves `\.extensionRelayUseCase` directly — the one Entry → UseCase edge in the graph — and the key-path lint carries it as a named, permanent exception. A pass-through Interactor was rejected: the pass-through Repositories (`ExtensionInstallRepository`, `PreviewRepository`) keep a layer every process has, whereas an extension Interactor would add a GUI lane to a process that has no GUI.
