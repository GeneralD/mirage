# Architecture

macOS menu-bar app: webcam → real-time Metal shader effects → virtual camera. Clean Architecture in the lyra style, with SwiftPM targets enforcing layer boundaries at compile time and every physical element behind a port so the test suite is deterministic.

> This is the canonical architecture reference. `.claude/CLAUDE.md` keeps a short summary and points here; the **enforceable** boundaries live in `.claude/rules/architecture-boundaries.md` and `.claude/rules/physical-abstraction.md`.

## Architecture Decision Record

**Context.** The product replaces the discontinued Snap Camera on macOS: webcam frames are processed by GPU shaders and served to any video-calling app as a virtual camera. Effects must be loadable at runtime from community-authored `.lens` packages (MSL source compiled with `MTLDevice.makeLibrary(source:)`), so untrusted GPU code is a first-class input. The only sanctioned virtual-camera mechanism is a CoreMediaIO Camera Extension (macOS 12.3+; DAL plug-ins were disabled in 14.1), which runs sandboxed in a second process, so a host → extension IPC is unavoidable. The author's lyra codebase proved a pattern — one SwiftPM target per layer slice, swift-dependencies DI, every OS boundary a port, a shared TestSupport with event-driven waiting — that keeps a large module graph testable without flaky tests; the sibling decoy project proved the CMIO/System Extension/Mach-port plumbing. Solo developer, rich domain (frame pipeline, effect lifecycle, GPU failure policy, IPC), AI-assisted development that relies on tests as the specification.

**Decision.** Clean Architecture with the lyra layer vocabulary (Entity → Domain → UseCase → Repository → DataSource/DataStore → Gateway, plus Interactor → Presenter → View/Router lanes for the GUI). swift-dependencies for DI with one wiring target per process. All physical elements (camera, GPU, compiler, IOSurface, Mach, System Extension, CMIO stream, files, watch, clocks, host time, randomness, defaults, logging, display link, global hotkeys, the login item, image decode and encode, the process log store, standard output and error, the host's app and macOS versions) are Domain ports with fake doubles in a shared `TestDoubles` target. No actors on the frame path; frame flow runs on an injected `FrameExecutor` and surfaces travel as pooled, generation-tagged leases. The Xcode project is a thin xcodegen shell that embeds the Camera Extension; all logic is SPM. Product name is confined to three files.

**Consequences.** Tests are fully deterministic and run in parallel without a GPU; the module count is high (`Package.swift` lists some eighty non-test targets) and every new module touches `Package.swift`, DI and docs (the checklist is mandatory). The real GPU and the real extension are exercised only in a separate local test job and a manual verification lane. Zero-copy frame transport depends on the `SurfaceToken` + Mach-port design surviving the M0 spike; the fallback is one copy per frame. Renaming the product is a three-file change plus profile re-issue.

## Frame Path

```text
AVCaptureSession ──(CaptureSessionGateway, serial queue)──▶ CameraDataSource ──▶ CameraRepository
   ▼ FrameRef + SurfaceToken
FramePipelineUseCase  (LatestFrameSlot → tick() on FrameExecutor → one effect pass in flight via WorkRunner; a busy tick drops its frame; any failure sends the input; while bypassed, a tick sends its frame as it is instead of starting a pass)
   ├─▶ EffectRuntimeRepository ──▶ ShaderCompilationDataSource ──▶ ShaderLibraryGateway (makeLibrary(source:))
   │   (orchestrates, no state)    ├▶ GPURenderDataSource ──▶ GPUGateway (encode / commit / completion)
   │                               ├▶ EffectRuntimeStateDataSource (in-process cache keyed by source, compile options and parameter layout, newest wins, the selected effect's parameter block, session clock and seed; hops onto FrameExecutor)
   │                               └▶ BundledEffectDataSource (the bundled effects' MSL, string constants; the first is the default)
   │   each pass's outcome (the timing or the failure, stamped with the fingerprint of the effect that ran) is reported to EffectRuntimeStateDataSource and leaves it as the outcomes() stream, which EffectCatalogUseCase feeds to EffectHealthPolicy off the frame path
   │   the frame that goes on (output, or input on failure) fans out: sent first, then presented; its lease ends with the later of the two
   ├─▶ VirtualCameraRepository ──▶ FrameTransportDataSource ──▶ MachGateway (IOSurface mach port, MOVE_SEND)
   └─▶ PreviewSink (host, same frame, completion ends the lease; in split mode also the pass's input as the original, whose lease ends with it) ──▶ PreviewRepository ──▶ PreviewDataSource ──▶ PreviewGateway (MetalKitPreviewGateway: one compute pass into the view's CAMetalLayer drawable, the frame alone or split against its original)
                                   ║ process boundary (sandboxed Camera Extension)
ExtensionRelayUseCase ◀── FrameReceiverRepository ◀── FrameReceiverDataSource ◀── MachGateway (check-in, receive: frame / hello / dead-name)
   └─▶ StreamOutputRepository ──▶ StreamOutputDataSource ──▶ CMIOExtensionGateway (CMIOExtensionStream.send)
   (host lost → SlateSchedule: black frames from a per-episode slate surface, ticked by FrameScheduler, until a newer real frame arrives)
```

The host also keeps a presence port alive toward the extension and reconnects on its own when the extension goes away (see *Host absence and slate* and *Host reconnect* below). Pixel buffers never cross a layer as `Data` or as raw `IOSurface`; the one exception is a `StillImage` (BGRA bytes, rows packed), which `SurfaceRepository.upload` / `download` copy into and out of a pooled surface for the authoring tools, so a still image can go through an effect without a camera. The host and the extension each own a `SurfaceRepository`; a surface only crosses the process boundary as a Mach port and is re-leased on the other side.

## Target Layout

- **SPM (`Package.swift`, tools 6.0, macOS 14)** — every module above as `.target` + `.testTarget`; external dependencies: swift-dependencies, swift-clocks (tests). The executables are `DevHarness` (product `dev-harness`), `ViewGallery` (product `view-gallery`) and `LensTool` (product `lens-tool`, the offline authoring command line over `EffectAuthoringInteractor`: validate, scaffold and render a still, no camera); none is a shipped product, since no xcodegen shell links them. `make build-dev-harness` builds the first and the CI release-build job runs that after `make build`; `scripts/gallery` builds `view-gallery` with `swift build --product view-gallery`, and `swift run lens-tool` runs the third. `make build` compiles all three too: SwiftPM ignores `--product` for the automatic `App` / `ExtensionApp` library products and builds every non-test target. `make build` always passes `--product`.
- **Xcode shell (`project.yml` → xcodegen; `*.xcodeproj`, `Info.plist` and `*.entitlements` are generated and gitignored)** — target `Host` (application; sources `Apps/Host/`, embeds the extension with `codeSign: true`) and target `CameraExtension` (`system-extension`; sources `Apps/CameraExtension/`). Product names, bundle IDs, plist properties and entitlements are declared in `project.yml`; target names are role names.
- **Signing** — Debug ad-hoc; Release Developer ID + two provisioning profiles (app, extension), notarized DMG via the release workflow copied from decoy (never exercised there — M0 includes its first real run).

## Key Design Decisions

**Rename-safe naming.** The product name appears in exactly three files: `README.md`, `project.yml` (`name`, `PRODUCT_NAME`, bundle IDs) and `Sources/Entity/ProductIdentity.swift` (display name, host and extension bundle IDs, Mach service name, log subsystem, virtual device UUID — plain literals, because `project.yml` and the provisioning profiles need the same literal strings and `scripts/check-service-names.sh` compares them textually). Module, target, type, file and directory names are role names. The shells' `Info.plist` and entitlements necessarily carry bundle IDs, so they are **generated** by xcodegen from `project.yml` (`info:` / `entitlements:` properties) and gitignored — never hand-written. The one hand-written plist, the dev harness's (*Dev harness* below), carries a role-named bundle ID and no product name. Renaming = editing those three files + re-issuing the two provisioning profiles (bundle IDs and the Mach service name are baked into them — an Apple constraint, not a code one) + `gh repo rename`. `make check` fails if the product name string appears anywhere else under `Sources/`, `Tests/`, `Apps/`, `Tools/` or `Examples/` (the sample `.lens` packages): Swift and Metal sources under the first three, every file under `Tools/` and `Examples/`, file and directory names throughout.

**Gateway modules for every OS boundary (lyra, not decoy).** decoy hid OS types behind inner ports inside adapters; here each boundary is its own `*Gateway` module consumed at the DataSource layer (the execution-context ports — `frameExecutor`, `frameScheduler`, `workRunner`, live in `DispatchExecutorGateway` — are the exception: the UseCases run the frame path on them, and the key-path lint names them), so the import lint can draw a hard line: AVFoundation, Metal, MetalKit, IOSurface, CoreMediaIO, CoreMedia, CoreVideo, SystemExtensions, Carbon, ServiceManagement, ImageIO, CoreGraphics, OSLog, AppKit and `os` are importable only in Gateway modules and the View/Router/App lane.

**No actors on the frame path; tokens instead of surfaces.** decoy hit a Swift 6.3 crash passing `IOSurface` across an actor boundary and fell back to `Data` frames (up to four full copies per frame). Here frame callbacks run synchronously on the `FrameExecutor` port (live: one serial queue), UseCase frame state is a single-threaded state machine (no locks in UseCases), and pixel storage is referenced through `SurfaceToken` — an `(index, generation)` value issued by `SurfaceRepository` / `SurfacePoolDataSource`. The generation is what makes the token safe without a scoped wrapper: a token whose generation no longer matches the slot resolves to nothing, so a double `release` or a use after release is detected (`release` returns `false`) rather than touching the slot's next tenant. Tokens are process-local and never serialized; a surface crosses the process boundary only as a Mach port. Property test: after stop, `liveCount == 0`; any allocate/release sequence never double-frees. To be validated in the M0 spike; fallback is a single copy at the transport.

**Latest-frame slot + tick, not per-frame fan-out.** Capture callbacks only overwrite a `LatestFrameSlot`; the pipeline consumes it on `FrameScheduler.tick()` with an in-flight cap of one effect pass (see *Effect stage* below). Heavy encoding never runs on the capture callback, and interleavings are enumerable in tests (`ManualFrameExecutor.drain()` + seeded `forAll`). A TSan job (`swift test --sanitize=thread`) runs nightly.

**Effect stage: one pass in flight, two leases, pass-through without memory.** Owner: `FramePipelineUseCase`. A tick takes the slot's frame, leases an output surface of the same descriptor from `SurfaceRepository` and starts `EffectRuntimeRepository.apply(input:output:frameContext:)` through the `WorkRunner` port; the answer hops back onto the `FrameExecutor`, where the pass (`EffectPass`: input, output, and the stop count its run started under) lives. *In-flight cap = 1:* frames that arrive while a pass runs wait in the slot (newest wins, as always), and a tick that finds a pass still running drops the frame it took as `.inFlightCapReached` instead of holding it across the tick — so every frame a tick takes ends as exactly one send or one counted drop (or is abandoned by `stop`), which the seed property checks as a conservation law. *Leases, each released exactly once, and only the answer ends a pass:* on success the input is released at the answer and the output goes on (in the preview's split mode the input goes to the preview as the frame's original and is released with it, *Preview fan-out* below); on any failure the unused output is released at the answer and the input goes on unchanged. The frame that goes on is released once the sink and the preview are both done with it (*Preview fan-out* below). An output that cannot be leased (pool exhausted, or an allocation error) drops the frame as `.poolExhausted`. *No failure memory:* every frame is judged on its own answer; consecutive-failure counting and auto-disable belong to `EffectHealthPolicy` in `EffectCatalogUseCase`, which the runtime's outcome stream feeds (*Effect health* below). *Stop abandons the pass; it cannot cancel it:* cancelling cuts no GPU work short, so the live runtime may still read the input and write the output after `stop()`. `stop()` first bumps a stop count (a `CurrentValueSubject`, so the bump is visible at once from any context), and an answer from a pass started under an older count only ends the pass — even one already queued on the executor ahead of `stop()`'s cleanup — so nothing is sent after `stop()`. A pass carries the count its run's `start()` read, which every tick of that run is handed, never a count the tick reads itself: the live ticks fire on the executor's queue while `stop()` runs on the caller's thread and bumps the count before it waits for the tick under way, so a tick reading the count would adopt the new one and send after `stop()` (or into the next run). The abandoned pass keeps both leases and the in-flight cap until its answer, which releases both with nothing sent, shown or counted; the cleanup's `releaseAll()` waits for that answer and for every frame still on the preview (and is left out once a restart owns the pool), and a restarted pipeline's ticks drop as `.inFlightCapReached` while the abandoned pass is still out. `PipelineStats` counts every drop by reason (the extension's slate drops included, so the reasons add up to `framesDropped`) and effect outcomes by failure kind. The effect half of that bookkeeping (`noteEffect`, `effectsFailed`, `effectSummary`) is host-only policy and lives in `FramePipelineUseCase`; `note`, `noteReceived` and `summary` stay in `Entity` because both UseCases use them and neither may depend on the other. The developer log carries a per-second `effect` line (`applied=… failed=… <kind>=… capDropped=…`) next to the `pipeline` summary. Drop lines are deduplicated per source — the effect stage and the transport each log a reason only when it changes, and `start` and `.connected` make every reason news again — and the operational failure behind a drop (an exhausted pool) reaches the error log by the same rule, once rather than once per frame. The pipeline never calls `prepare(effect)` either: `EffectCatalogUseCase` does (*Effect catalog* below), and until it has prepared anything the runtime prepares the bundled effect on the first `apply` (*Effect runtime* below).

**Preview fan-out: the frame that goes on is sent, then shown; its lease ends with the later of the two (epic #14, D9).** Owner: `FramePipelineUseCase`, through the `PreviewSink` port (`\.previewSink`, the Repository-layer port next to `VirtualCameraSink`). The pipeline owns both leases of a pass, and the frame that goes on — the output on success, the input on any failure — is handed to `VirtualCameraSink.send` and then to `PreviewSink.present`, and released once both are done with it, exactly once. The send returns synchronously, so presenting after it reduces "both" to the preview's completion: that completion may run on any thread and at any point, so it hops onto the `FrameExecutor` and the lease ends there. With no view attached the live `PreviewDataSource` queues the frame on the executor and completes it in that job, after `present` has returned; `InMemoryPreviewSink(holding: .onceAttached)` completes inside `present` itself, the stricter case, and the pipeline's tests run on it (`LoopbackRig(preview: .rendered)` runs the live timing). A frame the sink refuses (not connected, queue full) is still shown and its drop counted as before: the preview is the host's own view of the camera, not a mirror of the link. The preview holds that lease and, in the split mode, the pass's input as the frame's original (`PreviewSink.present(_:original:completion:)` borrows both until its one `completion`, which ends both leases; the virtual camera never sees the original), and nothing else — the in-flight cap ends at the answer — so a preview slower than the camera delays no pass and no send; what it costs is pool surfaces, which `PreviewDataSource`'s latest-wins bounds at two presented frames (one drawn, one waiting, each with its original in the split mode) within the live pool of eight, and which in the pipeline's pool of four tests runs the pool out: the camera is refused or the output lease drops as `.poolExhausted`, and nothing leaks. `stop()` does not abandon a frame already on the preview (it was sent before the stop); its pool reset waits for every such frame as it waits for an abandoned pass — an executor-confined count of frames on the preview — and the last completion or answer to arrive after the cleanup runs it, unless a restart owns the pool by then. The conservation law is untouched: the preview neither sends nor drops, so every frame a tick takes is still one send, one counted drop or one abandoned pass. Alternatives not taken: presenting before sending and joining two completions with a per-frame count, which only an asynchronous `send` would need; and skipping a presentation while an earlier one is outstanding, as the harness's retired solid-frame UseCase did — the DataSource's latest-wins already bounds what the preview holds, and the pipeline would duplicate that policy. Proven by `FramePipelinePreviewTests` (late completion, sink first, no view attached, stop and restart with a frame on the preview), a 50-seed property over emit / tick / effect answer / send / preview completion / attach / stop / restart, and `FramePathIntegrationTests` running the real `PreviewRepository` / `PreviewDataSource` over `FakeGPUGateway` + `FakeShaderLibraryGateway` + `FakeTextureCacheGateway` + `FakePreviewGateway` on the loopback's host side.

**Two time sources, one rule.** Sleeping, debouncing and timers use `\.continuousClock` (lyra); PTS uses `HostTimeProvider` (mach uptime, required by `CMIOExtensionStream` `.hostTime` clocks — decoy observed Zoom freezing when PTS was `0` or "now"). To keep `TestClock` and `FixedHostTime` from disagreeing, slate frames derive PTS as `base + n × (1/fps)` from one captured base, and uniform `time` is `PTS − sessionStartPTS` in seconds (`EffectSession`). No wall clock anywhere.

**Runtime MSL compilation through our own pipeline, not Core Image.** `CIKernel(source:)` is deprecated and Metal `CIKernel`s need pre-built metallibs; `MTLDevice.makeLibrary(source:options:)` is the only runtime path. `ShaderCompilationDataSource` (port `ShaderCompiler`) prepends the prelude (`Uniforms`, hash/noise helpers) and one generated `Parameters` line (*Effect parameters* below), with `#line` so diagnostics map back to the author's lines, and runs the compile off-main inside a `WorkRunner` item (the fake gateway records the thread and fails the test otherwise). It caches nothing — the cache and "newest wins" are `EffectRuntimeStateDataSource`'s — and cancellation does not shorten a compile: the caller stays suspended until the compiler finishes and receives the real result (pinned by `ShaderCompilationDataSourceTests`, mirrored by `FakeShaderCompiler`), so dropping a stale handle is the state's decision (`EffectRuntimeStateDataSource` compares tickets), never a side effect of cancelling its task. It asks `GPUGateway` for a fresh context per compile: compiles are rare, the compile needs only the device, and the handle it returns (the pipeline state) dispatches on any context of that device, so no context is shared across concurrent compiles and no lock is needed. **`#line` diagnostic mapping:** the assembled source is the prelude, `#line 1 "effect"`, then the author's source verbatim (`ShaderSourceAssembly`, pure), so the compiler numbers the author's lines from 1 under the file name `effect`; `MetalGateway smoke` proves it on the real compiler on every `test-gpu` run (a syntax error on the author's third line comes back as `effect:3:`, not as its line in the assembled source). On top of that the DataSource rewrites any location still given against the assembled source: `program_source:<n>:` inside the author's part becomes `effect:<n − offset>:` — the safety net should a compiler ignore the directive, property-tested over 50 seeds of source length and error position — and inside the prelude becomes `prelude:<n>:`, so the note under an author's redefinition of `hash` says where the original lives. Only a location that opens a diagnostic line is rewritten: the compiler echoes the failing source line verbatim, so `program_source:<n>:` inside that excerpt or inside a message is the author's text and is kept. **The prelude** declares `Uniforms` (mirrors `EffectUniforms`; `static_assert(sizeof(Uniforms) == 24)` turns a drift into a compile error of every effect), `hash(cell, timeStep, seed)` (white noise in [0, 1) at 24-bit resolution from integer avalanche rounds, so bit-exact against the Swift twin) and `noise(p, time, seed)` (value noise, trilinear over the hash lattice in space and time with smoothstep weights; IEEE adds and multiplies, so within one 8-bit step once the GPU fuses a multiply-add); internal helpers live in `namespace prelude`, and the prelude never defines the entry point. `HashNoiseReference` (`Tests/TestSupport`) is the Swift twin, operation for operation; the `hash-noise parity` GPU suite compares every pixel of a 256 × 256 image for seed 0 and another seed under the GPU suites' single tolerance, and the hash's 24 bits bit for bit.

**Effect runtime: a Repository that orchestrates, over a state confined to the executor (epic #14, D1 / D14).** Owner: `EffectRuntimeRepository` (`EffectRuntimeRepositoryImpl`, a stateless struct); memory: `EffectRuntimeStateDataSource`. *Where the state lives.* The compile cache, the selection, the ticket counter, the callers waiting for the selection and the session clock must change together, in one step, so they are confined to the `FrameExecutor` (thread confinement on a serial executor): there is no lock, which the lint forbids above the Gateway, and no actor, which the frame path avoids and which would take `ManualFrameExecutor.drain()` away from the tests. A Repository does not reach for the executor, so the state is a DataSource — the precedent is `SurfacePoolDataSource`'s slot bookkeeping and `GPURenderDataSource`'s hop onto the executor — behind the `EffectRuntimeState` port, whose every call hops there itself, decides in one step and hops back. A UseCase was ruled out because it sits above the Repository (the Repository would have to call upward, or the pipeline would hold a second UseCase for one runtime: UseCase → UseCase); a `DataStore` is, in this repo, persistence over a Gateway (`PreferencesDataStore`), and these transitions are not storage. The price is one more module, and an `EffectTicket` crossing the port so that "newest wins" is decided in the state while the slow compile runs in the Repository. The Repository resolves `effectRuntimeState`, `shaderCompiler`, `gpuRenderer`, `bundledEffects`, `workRunner` (the lifetime of the compile an `apply` starts) and the two logs; its suite is wired without any executor, so one that reached for it would meet the unimplemented default. *The cache* is keyed by `(source, compile options, parameter layout)` — a `Hashable` key of the three, so a hash collision still compares the sources — and never by the effect's name, so a label or a default that changes recompiles nothing; only successful compiles are kept, so a broken source compiles again when it is prepared again. It lives in process only: a cache on disk, which would need a device id, an OS version and a `RuntimeEnvironment` port to supply them, is deferred to Later (epic #42, D12, which supersedes the plan of epic #14, D14), so no implicit port exists here. *Newest wins:* every `begin` takes the next ticket, and `apply` runs the effect of the newest one, whether it compiled or failed. A compile that finishes after a newer `prepare` still answers its own caller with its real outcome (the port's contract) and a success still fills the cache, but it never becomes the effect `apply` runs and never releases a caller waiting for the newer one; a cache hit settles at once, overtakes a compile still running and releases the callers that waited on it. The state suite proves these rules through the port with the completions written down in either order, and mutations of the ticket check, the cache write and the waiter release (by a compile and by a cache hit) turn it red. The Repository suite proves what the Repository decides over the real state: which port each call goes through, what it maps and logs, that a `prepare` which overtakes an `apply`'s own compile answers that `apply` without waiting for the compile, and that it resolves no executor (a mutation that does turns it red). *The bundled default:* while nothing has been prepared (the effects menu prepares the chosen effect as soon as its run has listed the catalog) the first `admit` hands back `BundledEffects.defaultEffect` (asked of the Repository through a closure, only then) to be compiled; the pipeline never learns the effect exists. An `apply` that meets the newest compile still running waits for it (one slow pass, during which the pipeline's in-flight cap drops ticks as `.inFlightCapReached`) rather than answering a failure the stats would count. An `apply` that compiles an effect itself starts that compile on the `WorkRunner` and waits for the *selection*, not for its own compile: when a newer `prepare` settles first, the frame goes on with the newer effect instead of waiting out a stale compile (and holding the in-flight cap for it), and the late compile still fills the cache and the log. The compile holds no lease, so the leases stay the caller's until `apply` returns. *Two kinds of failed compile.* A source that does not compile is the effect's fault: `.compileFailed`, final for the frames after it, which answer at once without compiling again, so a broken effect costs one compile and the pipeline passes every frame through. A compile that found no GPU context, or whose compiler service failed (`ShaderDiagnostics.cause == .environment`), is the runtime's: `.internalError`, as the renderer answers for the same cause, which keeps a good effect from being counted as a broken one, and not final — the selection remembers the effect and the next `apply` compiles it again, as the next pass asks for the render context again. Those retries run at the camera's pace, so the state counts a streak of them and the Repository logs only its first failure and the recovery ("compiled after N failed attempts"), the pipeline's rule for drop reasons: a change is news, a repeat is counted. `ShaderCompilationDataSource` marks the missing context as `.environment` itself and classifies the compiler's own errors by their raw code, with the pure `LibraryErrorMapping` (epic #42, D7): `MTLLibraryError.internal`, a transient fault of the Metal compiler service, is `.environment` too, and every other code, the `0` of a missing entry point included, is `.source`. A thin Gateway does not classify, so `ShaderLibraryGateway` returns the raw code and nothing else; the number is spelled out because nothing above the Gateway imports Metal, and `LibraryErrorCodeTests` pins it to the SDK the way `GPUCompletionMapping`'s codes are pinned. Classifying only the compiler's answer keeps a missing context `.environment` whatever its own code would read as. It matters once `prepare` is called by the effects menu's hot reload: a compiler service fault in the middle of an edit is retried by the next `apply` instead of being final, while a source that does not compile stays final. *The bundled effect is a string constant (D1):* `BundledEffectDataSource` holds `ChromaticGrainEffect`'s MSL in Swift and returns it as an `EffectSource`, so there is no `Bundle.main`, no bundle port and no resource bundle in the Xcode shell; `.lens` packages come from `EffectPackageDataSource` (#45) behind the same `EffectSource`, so the runtime's contract does not change. The effect drifts red and blue sideways by 1 to 4 pixels (the prelude's `noise` over 64-pixel bands and over `time` at half speed, sampled with a linear blend so the drift has no steps) and adds a per-frame grain (`hash` of the pixel and `frameIndex`); `MetalGateway smoke` compares one pass with its Swift twin (`ChromaticGrainReference`) under the GPU suites' one tolerance, directly and through the runtime over the live DataSources. *Uniforms* (`EffectUniforms.pass`, pure, built by the state when it admits the frame): `time` is seconds since the session's first frame as a `Float` (`EffectSession`: a session starts at frame index 0, which the pipeline counts from again at every `start`, or at the first frame the runtime is handed; a frame stamped before its session's start is at 0), `frameIndex` is the caller's, `resolution` is the output surface's size in pixels, and `seed` is the session's, drawn once from `RandomSource` when a frame starts the session and kept until the next one (D3; `EffectSession`). The pass's grid is the output size rounded up to whole 16 × 16 threadgroups (`DispatchGrid.covering`), so it can overshoot `resolution` and a kernel bounds-checks its `gid` against the texture, as the bundled kernel does.

**Every host port above the OS boundary has a live value from the day its contract exists.** `EffectRuntimeRepository` and `PreviewSink` were registered the moment their protocols landed, as `PassthroughEffectRuntimeRepository` (`prepare` and `apply` answer `.failure(.internalError)`: the runtime, not the effect, is what is missing, and the pipeline passes the frame through) and a discarding sink (`present` completed at once). Each lived in the module the real implementation would occupy, so #19 / #20 replaced the `liveValue` in place and a PR merged ahead of them never left the host without a runtime or a sink. Both have: the sink is `PreviewRepositoryImpl` over `PreviewDataSource` (which itself completes every frame, undrawn, in an executor job until a view is attached), and the runtime is `EffectRuntimeRepositoryImpl` over `EffectRuntimeStateDataSourceImpl` (*Effect runtime* above), which took `PassthroughEffectRuntimeRepository`'s place and its module. The fakes that the DataSource and UseCase suites drive (`FakeGPUGateway`, `FakeShaderLibraryGateway`, `FakeTextureCacheGateway`, `FakeEffectRuntimeRepository`, `InMemoryPreviewSink`, `FakePreviewGateway`) complete manually and in any order, refuse foreign handles with the live gateways' errors and in the live gateways' order, and are themselves under contract test (`Tests/TestDoublesTests`), so a lenient fake cannot hide a bug the live gateway would raise. Every manual-completion fake (`FakeGPUGateway`, `FakeEffectRuntimeRepository`, `FakeGPURenderer`, `FakeShaderCompiler`, `InMemoryPreviewSink`, `FakePreviewGateway`) tags what it issues with its own `ObjectIdentifier`: ids restart at 1 per instance, so a completion handed to another instance returns `false` (`nil` from `FakeShaderCompiler.succeed`; a reported issue from the two gateways) and resumes nothing. Two things are deliberately *stricter* than live. The live `TextureCacheGateway` holds no state and cannot see a double unbind, while `FakeTextureCacheGateway` throws on it and counts it (`doubleUnbindCount`), so the DataSource's exactly-once unbind is proven against the fake rather than trusted to the device. And `InMemoryPreviewSink(holding: .onceAttached)` completes a frame inside `present` where the live `PreviewDataSource` completes it in a later executor job, so the pipeline's hop onto its executor is proven against the caller-still-inside-its-own-call case, while `LoopbackRig(preview: .rendered)` keeps the live timing covered.

**The effect catalog follows the same rule (epic #42, D10).** Seven modules exist from the day their contracts do, each with a small pass-through that the later issues replace in place: `NoPackages` (`EffectPackageDataSource`: an empty inventory, no package, `openFolder` does nothing; #45 replaced it in place with `EffectPackageDataSourceImpl`, *`.lens` packages* below), `NeverChangingWatch` (`EffectWatchDataSource`: a stream that yields nothing; #46 replaced it in place with `EffectWatchDataSourceImpl`, *Hot reload, the watch half* below), `EmptyPreferences` (`PreferencesDataStore`) and `EmptySettings` (`SettingsRepository`), which kept nothing and reported no stored selection until #51 replaced them in place (*The chosen effect is kept as one string in the user's defaults* below) and `StaticEffectInteractor` (`EffectInteractor`: publishes a fixed state, or none, and its commands do nothing; #49 replaced it in place with `EffectInteractorImpl`, *The effects menu's Interactor and Presenter* below). `EffectPackageRepository` had one too, `BundledOnlyCatalog`, and #47 replaced it in place with `EffectPackageRepositoryImpl` (*Effect catalog* below). The seventh, `BundledOnlyEffectCatalog` (`EffectCatalogUseCase`: the bundled catalog with its first entry selected, `select` `.prepared` for a listed id, `run()` parked), has been replaced in place by `EffectCatalogUseCaseImpl` (#48, *Effect catalog: the UseCase selects and reloads* below). `HostDependencyInjection` registers them and `HostEffectRegistrationsTests` pins what each stateless key resolves to, the real implementation of its module (`EffectPackageDataSourceImpl` for `effectPackages`, #45; `EffectWatchDataSourceImpl` for `effectWatch`, #46; `EffectPackageRepositoryImpl` for `effectPackageRepository`, #47; `SettingsRepositoryImpl` and `PreferencesDataStoreImpl` for `settingsRepository` and `preferences`, #51; `EffectInteractorImpl` for `effectInteractor`, #49; `EffectCatalogUseCaseImpl` for `effectCatalogUseCase`, #48; the last two are pinned by `HarnessLiveWiringTests`, below). The OS-boundary lives are pinned by `HostFileGatewayRegistrationsTests`, which resolves each one inside `context = .live` with nothing overridden and never calls it (a call would read the user's defaults): `FileSystemGatewayImpl`, `FileWatchGatewayImpl`, `WorkspaceGatewayImpl`, `AppDirectoriesProviderImpl` and `KeyValueStoreGatewayImpl` (#51) for `fileSystemGateway`, `fileWatchGateway`, `workspaceGateway`, `appDirectories` and `keyValueStoreGateway`. The default graph shows the bundled effect and whatever packages the effects folder holds, and watches that folder; since #45 the first catalog it asks for lists the effects folder (and makes it), and since #46 the run arms a watch on it through `FileWatchGateway`, which is why `HostEffectRegistrationsTests` resolves every stateless live value inside a `live(_:)` scope over an in-memory file system, a fixed folder, a `FakeFileWatchGateway`, an in-memory key-value store, a `FakeWorkspaceGateway` and fresh logs, and no suite ever touches the user's own folder, defaults or Finder, or opens a real descriptor; the suite asserts it for the folder, the descriptor and the defaults by reading the fakes back (the default-graph test: the effects folder made once, then listed, its directory watch armed on the `FakeFileWatchGateway` with no "could not watch" line, and no error logged; the restore test: a package choice seeded in the in-memory store comes back as the selection), while Finder is only overridden, since nothing here calls `openFolder` (`HarnessLiveWiringTests` drives it to the fake workspace). *Who resolves which live value.* A live value is a process-wide `static let`, built on its first resolution, and the test bundle is one process whose suites run concurrently. The Repositories, DataSources and DataStore are structs that hold nothing between calls, but a call made outside a scope of its own reaches the Gateways the first builder's scope held, and which suite built first is a race; so every suite that resolves them does so, and calls them, inside a `withDependencies` scope that overrides each Gateway they reach, and a `Task` made inside inherits it. `EffectInteractorImpl` (it resolves the catalog and the logs once and starts a supervising `Task`) and `EffectCatalogUseCaseImpl` (it owns the catalog's session) freeze the scope that built them for the process, so exactly one suite in the whole test bundle resolves them live: `HarnessLiveWiringTests`, which also checks their types there. `scripts/check-live-owner.sh` (in `make check`) fails when any other test file names either key as a key path (`\.effectInteractor`, `\.effectCatalogUseCase`; an override assigns and resolves nothing) or calls `HarnessMenu.live()` (the harness's route to a live `AppRouter()`, whose Presenter resolves `effectInteractor`; the grep reads comments too, so no other file spells the call); a live `AppRouter()` or `EffectInteractorImpl()` made directly, which resolves the key through its own `@Dependency`, is not seen, and stays with review. `HostEffectRegistrationsTests` pins the stateless values and builds its own `EffectCatalogUseCaseImpl` for the default-graph test, and resolves neither of the two keys. It reads the stored choice only when a run starts (`EffectCatalogUseCaseImpl` is the first client of `settingsRepository`) and writes it only when `select` is called. They respect the key-path lanes: the UseCase reads the catalog through `effectPackageRepository`. No pass-through of the catalog remains, and the real DataSources resolve only OS-boundary ports that already have a live value (`FileSystemGateway`, `AppDirectoriesProvider`, `WorkspaceGateway`, `FileWatchGateway`), so an OS-boundary port that has no live value yet is never reached: the rule above is about the ports above that boundary, and a Gateway or Support live arrives with the issue that wraps its OS API. `FileSystemGateway`, `FileWatchGateway`, `WorkspaceGateway` and `AppDirectoriesProvider` (module `AppDirectories`) landed in #44, so `EffectPackageDataSource` found them registered when it replaced its pass-through (#45) and `EffectWatchDataSource` found `FileWatchGateway` registered when it replaced its own (#46); `KeyValueStoreGateway` landed in #51 as `UserDefaultsGateway`, which `PreferencesDataStoreImpl`, the replacement of `EmptyPreferences`, resolves. `NeverChangingWatch.changes`, the one stream-returning pass-through, left its stream open until the consumer let go, and `EffectWatchDataSourceImpl` keeps that contract, because the end of a stream is the cleanup signal and would read as "the source died". The fakes that stand in for these ports under the later suites are themselves under contract test (`Tests/TestDoublesTests`): a stream they hand out is registered before the call returns, `terminations` counts the consumer letting go, and `FakeFileWatchGateway` counts a double stop.

**The file gateways throw instead of branching, and are proven by smoke (epic #42, D2 / D4, #44).** The thin-live rule forbids `if` / `guard` / `var`, so each place an OS call can fail or answer an optional is settled by the call's own shape. `FileWatchGatewayImpl` opens its descriptor with `FileDescriptor.open(…, .eventOnly)` from the System module, which throws for a path that cannot be watched; lyra's gateway tests the raw `open` result and returns `nil`, a branch this live does not have, and the port promises the throw. `FileSystemGatewayImpl.isDirectory` reads `URL.resourceValues(forKeys: [.isDirectoryKey])` (the `FileManager` form needs an inout `var`) after `resolvingSymlinksInPath()`: the plain resource value is `false` for a symlink to a directory while `contentsOfDirectory` lists it, so a package linked into the effects folder would be listed but skipped. `FileSystemGatewayImpl.readData` reads with `FileHandle.read(upToCount:)`, which stops at the bound, so a file larger than its caller keeps is never read whole; it answers `nil` for a file with nothing to read, which `?? Data()` settles in the expression as `isDirectory` settles its optional with `== true`. `AppDirectoriesProviderImpl` takes `URL.applicationSupportDirectory`, the location `FileManager.urls(for:in:)` returns first, because it is not optional: there is no force unwrap and no fallback for an empty result that cannot happen. Watching has two descriptors because neither sees every save (a directory descriptor misses an in-place write to a file inside it, a file descriptor dies on a rename), and the smoke suite pins both halves, plus the shrinking truncate that posts only an attribute event (`.attrib` is in the mask for it). The suites assert "at least one" event, never a count, because the OS coalesces; a negative ("a stopped watch stays silent", "a directory watch does not hear an in-place write") waits on a sentinel watch that does hear the same write before it asserts. Every smoke suite of these two gateways runs in a UUID-named temporary directory that it removes; the one other suite that reads the disk, `ExamplePackagesTests`, only reads the repository's own `Examples/` (*Physical Abstraction Table*, the File system row).

**`.lens` packages: a folder, a manifest and one kernel (epic #42, D1 / D3).** A package is a directory `<id>.lens/` in the effects folder holding `manifest.json` and `effect.metal`; the id is the directory name without the suffix, so editing either file never changes who the effect is, and the menu shows the manifest's `name` (trimmed). *Alternatives not taken:* a single `.metal` file has nowhere to put a name or an author; a zip has to be unpacked, which defeats editing the shader in place and having it reload; a manifest that names its own shader file would make the watch set and the entry point open-ended for nothing, so the two file names are fixed, the entry point is `effect` and the compile options are the defaults (the thumbnail is the one file a manifest names, and what it adds to the watch set stays on its own path: *Thumbnails* below). *The manifest* (`EffectManifestDecoding`, pure) requires `formatVersion` (the integer 1, probed on its own first, so a newer package is reported as `unsupportedFormatVersion` even when its other keys have a shape this build would reject; a `formatVersion` that is a number but not an integer is `manifestInvalid` naming the key, `1.5` as not an integer and a whole number beyond `Int` as out of range, where the JSON decoder alone reports both as text that is not JSON, without a key) and a `name` that is not empty after the trim, takes `author`, `description` and `thumbnail` (a path inside the package, *Thumbnails* below) as optional, validates `parameters` (*Effect parameters* below) and ignores every other key: forward compatibility is the reason `formatVersion` exists, not strictness. Its `manifestInvalid` messages are built from the decoder's coding path rather than its wording, so they do not change with the OS or the locale. *A package that cannot be used is listed, not dropped (D3):* `EffectPackageDataSourceImpl` answers `.broken(id, problem)` so the menu can list a disabled item and say why in its second line (which macOS 14 may not draw, *Menu bar* below; the catalog's log carries the reason too, once per change, *Broken packages are logged on a change* below). It always reads both files and reports the first problem in a fixed order (manifest missing, unreadable, invalid; then shader missing, unreadable), so one broken file neither hides the other from the watch set nor makes the answer depend on read order. A file is *missing* or *unreadable* by its `CocoaError` code, never by a message. `fileReadNoSuchFile` is what `readString` raises, live (pinned by `FileSystemGatewayImplTests`) and in `InMemoryFileSystemGateway`; `fileNoSuchFile` is what `readData` raises for a missing thumbnail, live (`FileHandle`, pinned by the same suite) and in the fake, and for the two text files only a scripted `failRead` in `EffectPackageDataSourceTests` raises it. Every other failure, a non-Cocoa error included, is unreadable. *What to watch:* the folder and every package directory (as directories: an editor's atomic save only shows there) and every file that exists, the shader of a package whose manifest is broken included (as files: an in-place overwrite shows nowhere else); a missing file is not named because it cannot be watched, but its directory is, so creating it is noticed and the next listing watches it; a thumbnail adds its file and the directories on its way (*Thumbnails* below). *Folder, order and ids:* the first listing and `openFolder()` make the folder, `package(_:)` never does; the gateway promises no order, so the DataSource sorts by id in plain string order (the Repository orders for display); and since the id of a package comes back from a persisted selection (#51) and is joined into a path, `package(_:)` answers `nil` without touching the file system for an id that is not a `.package` id or not a single path component. *Where the checks end:* the DataSource proves that a package's files are readable and well formed; whether the kernel compiles is the runtime's (`prepare` answers `.compileFailed`, which the menu shows), and `Examples/Ripple.lens` is held to the format by `ExamplePackagesTests` (read through this DataSource it is ready, with a kernel named `effect` and no `Uniforms` of its own), while that its kernel compiles is not asserted by any test: it is checked on a device, in the Lane 1 run of #52 (`.claude/rules/dev-verification.md`, the timed table's steps 2 to 4).

**Thumbnails: a picture that can only be missing (#12).** Owner: `EffectPackageDataSourceImpl`, with the pure rules beside it in `EffectThumbnailReading`; the picker draws what it reads (*Effect picker* below). The value travels as `EffectManifest.thumbnail` (the path as written) → `EffectPackage.thumbnail` → `EffectCatalogEntry.thumbnail` → `EffectCatalogState`, which the effect picker reads; it is an `EffectThumbnail`, the file's bytes and an `EffectThumbnailFormat` (`png` / `jpeg`). The bundled effect has none, and neither has a broken package, whose manifest is not trusted for its name either. *Why bytes, not a path or a URL.* The picker lives in the View lane, which touches no file (`.claude/rules/physical-abstraction.md`), so the DataSource reads the file through `FileSystemGateway` and the bytes ride the catalog; turning them into pixels is the view lane's (`EffectThumbnailDecoding` in `AppRouter`, handed to the picker's view), and nothing below it imports an image framework. The bytes are checked only as far as their size and signature, so the picker must still expect a decode to fail, and it draws the effect's tile then (*Effect picker* below). *What is refused, and where.* The path is judged from its text before anything is read: an empty path, an absolute one, one that holds a NUL, or one with a `..` component (even one that would come back inside: nothing is resolved) is refused, and `.` and empty components are dropped. The text is split at the byte `/`, never by `Character`: a `/` followed by a combining mark is one `Character`, so a `Character` split would hide the `..` before it, while the kernel still splits there. The name must end in `.png`, `.jpg` or `.jpeg`, in any case. Then the file system is asked, still before anything is read: a directory on the way that is not there, or is a file, makes the file missing, and a directory where the file should be is refused (`is a directory, not a file`). Asking is not a nicety: below a file `FileHandle` fails with `fileWriteUnknown`, which would read as a file that cannot be read, and on a directory it has been seen to fail with `fileNoSuchFile`, `fileWriteUnknown` and `fileWriteNoPermission`, so its code is not one to sort by (`FileSystemGatewayImplTests` pins only that a directory throws, and that a path below a file does not throw a missing code). The file is read with `readData(_:upTo:)` and a bound of 1 MiB and one byte (`EffectThumbnailReading.readLength`), so a larger file is told from one at the limit without being read whole, and the bytes must begin with the PNG or the JPEG signature, which decides the format: a JPEG under a `.png` name is a JPEG, a text file under one is refused. *Why 1 MiB.* A picker cell is a few hundred points wide, which a 512 × 512 PNG fills well under the limit, while every listing reads every package's thumbnail again and every published state holds them all: the limit bounds what each package adds to the I/O of a listing and to the memory of a state, which grow with the number of packages and no faster. It does not bound what a picture decodes to, which the picker's decoder does itself (*Effect picker* below). *Symbolic links are followed*, as for `manifest.json` and `effect.metal` (and a package directory may itself be a link): the check keeps the path among the package's own names, the bytes never leave the process, and they must still carry an image signature. Refusing a link that leaves the package would take a gateway method that resolves one, and would refuse a link an author made on purpose. *A thumbnail that cannot be used costs the package its picture and nothing else.* The package is `.ready` with no thumbnail, and the reason is logged with the path quoted as Swift writes a string (`String(reflecting:)`, so a newline or a NUL reads as an escape): a file that is there and cannot be read is an error-log line, every other reason (a refused path, a file that is missing, a directory where the file should be, a file too large or not an image) a developer-log line, the same split as for a broken package. It is not a `.broken` reason because the effect itself works, and a picker that hid a working effect over its picture would cost more than the missing picture. A `thumbnail` that is neither a JSON string nor `null` is another matter: that is a manifest of the wrong shape, `manifestInvalid` naming the key as for `author`, and the package is broken with the reason in the menu. What the DataSource cannot know is whether the bytes decode: a thumbnail that was read but does not decode, or has more than 2048 × 2048 pixels in all, is the picker's to draw as the tile, and nothing is logged for it (*Effect picker* below). *What is watched.* A thumbnail that was read, or would have been had it been there, adds its file when it is there (an in-place save) and every directory on its way below the package directory that is there, whether the file is or not (an atomic save in a subdirectory, and the file or a directory on its way being made); a path refused by its text adds nothing, since only an edit of the manifest can change it, and neither does a directory where the file should be, whose replacement the directory it is in hears. *Read on every listing, cached nowhere*, like the shader, and a listing that changes only a thumbnail is a new catalog (`EffectPackageRepositoryThumbnailTests`) and a new state that prepares nothing (`EffectCatalogThumbnailTests`; on the loopback, `EffectCatalogIntegrationTests` fires the thumbnail file's own watch). *`package(_:)` leaves it out.* That read is the one a source is prepared from (`source(of:)`), for the chosen package on every listing and every choice; reading the picture there as well would read it a second time and log a second time why it cannot be used, for a value nobody takes, so `package(_:)` answers a ready package with `thumbnail` `nil` and the picture travels with `packages()` alone. *Missing by either code.* `FileHandle` reports a missing file as `fileNoSuchFile`, where `String(contentsOfFile:)` says `fileReadNoSuchFile`: the DataSource takes both as missing, `FileSystemGatewayImplTests` pins the live code (and `fileWriteNoPermission` for a file that may not be read, which the DataSource words as permission denied, as it does `readString`'s `fileReadNoPermission`), and `InMemoryFileSystemGateway.readData` raises it. `Examples/Ripple.lens` names a `thumbnail.png`, which `ExamplePackagesTests` copies byte for byte and requires to be read.

**Effect catalog: one listing per change, assembled in the Repository (epic #42, D3).** Owner: `EffectPackageRepository` (`EffectPackageRepositoryImpl`, a stateless struct); it resolves `effectPackages`, `effectWatch`, `bundledEffects` (DataSource ports) and the two logs, so it respects the Repository lane of the key-path table. *One round per change.* `catalog()` is eager: making the stream starts a task of its own, off the frame path (an unstructured `Task`, not the `WorkRunner`, whose business is the frame path's work), that runs a round and then another whenever the watch speaks. A round lists the folder (`packages()`), arms `effectWatch.changes(of: inventory.watchSet)`, shows the catalog and waits for the watch's first element. The watch is let go before the next listing and the next round arms the *new* inventory's set, never the old one, since a package that arrived or went away changes what there is to watch (D4: each package directory as a directory for an editor's atomic rename, its manifest, shader and thumbnail as files for an in-place overwrite, and the directories on a thumbnail's way as directories). The watch is armed before the catalog is shown, so the first change after any catalog a consumer has seen is heard. A re-listing is not covered: the old watch is let go before the folder is read again and the new one is armed only after that read, so an edit that lands after its file was read and before the new watch is armed is heard only with the change after it (the contract of `EffectWatch` arms everything before `changes(of:)` returns, but the set to arm comes from the listing, so listing and arming cannot be one step; the burst fold keeps the window to the few milliseconds of one listing, and the next save repairs it). The order of arming and showing is two adjacent statements, which a consumer on another thread cannot observe, so the suite pins it by sequence instead: thin wrappers around the two fakes write each call the Repository makes (listing the folder, arming a watch, and how many watches are still armed at that moment) to the developer log, between the "catalog listed" lines the Repository writes right before it shows a catalog, and the test reads back list, arm, shown, and after a change list, arm, shown again with no watch armed at either call. Ending the stream cancels the task, which lets go of the watch it armed (the end of a stream is the cleanup signal); a watch that ends *on its own*, which its contract never does, ends the catalog and logs an error instead of being listened to in a loop, so a catalog that has stopped being kept current is not mistaken for one that is. Whichever side ended it, the task records a developer-log line saying the catalog ended: the one signal that its work is done, which the ending tests wait for before they read the logs. *Every element is a listing, and every listing is shown.* The Repository does not compare a catalog with the one before (the one comparison it makes is of the broken packages, for the log alone, *Broken packages are logged on a change* below): folding a burst into one element is `EffectWatchDataSource`'s (a 200 ms quiet period on `\.continuousClock`), and a listing that looks the same can be a package whose `effect.metal` changed, which `EffectCatalogUseCase` finds out by reading `source(of:)` again. That is why `source(of:)` reads afresh on every call and caches nothing (D5: the comparison for a hot reload is between two reads). *Why the Repository decides the order and the bundled entry.* A DataSource knows one kind of source (the folder, the bundled effect) and promises no order; the catalog is the join of two of them plus a presentation rule, which is orchestration, and the UseCase above must see `[EffectCatalogEntry]` without knowing that there are two sources, a folder or a watch. The bundled effect is always first (D3: the fallback must exist and be findable); the packages follow by display name, compared case-insensitively with numeric runs as numbers (`Effect 2` before `Effect 10`), the folder name as the tie-break, and no locale, so the menu reads the same on every machine; a broken package is listed under its folder name, since its manifest cannot be trusted for one, as `.broken(problem)` among the others. *`source(of:)`* answers `BundledEffects.defaultEffect` for the bundled effect's id and `.sourceMissing` for any other bundled id; a package is read once with `EffectPackages.package(_:)`: `.ready` is `.success(source)`, `.broken` is `.failure(problem)`, and nothing at all (the folder is gone) is `.failure(.manifestMissing)`, the first thing a package lacks. `openEffectsFolder()` is `EffectPackages.openFolder()`. The suite is `Tests/EffectPackageRepositoryTests` over `FakeEffectPackages` and `FakeEffectWatch`: the first catalog needs no `fire()`, a re-listing is a `fire()` after `packages.script(_:)`, the old watch's end is `terminations`, and every wait is `Collector.waitForCount`.

**Broken packages are logged on a change, not on each listing (#71).** Owner: `EffectPackageRepositoryImpl`, in the task of each catalog stream: before it shows a listing, the Repository logs what changed about the broken packages since its last listing, and the DataSource logs nothing for a broken package, so `package(_:)` cannot repeat a line either. A package that was not broken, or whose problem is not equal to the one it had (its kind, or the reason it carries), is logged once: as an error when a file exists and cannot be read, as a developer line `package <id> is broken: …` otherwise; one that was broken and is ready is logged once as `package <id> is readable again`; a package that stays as it was is not logged again, however many changes list it, and one that left the folder is forgotten without a line. A listing with no packages in it forgets them all the same way, a folder that cannot be listed included: it gives an empty listing (the DataSource logs why), which the Repository cannot tell from an empty folder, so a broken package it hid is logged again when the folder lists. *Which layer remembers.* The memory is the sequence of listings, and the Repository is the layer that makes that sequence (`architecture-boundaries.md`). Three places were weighed. A DataSource: a live value is one process-wide `static let` that every suite and consumer shares (*Who resolves which live value*, in the D10 paragraph of the effect catalog), so a DataSource that remembered would let one catalog's listing silence another's, and its suites would have to reset it between cases. A UseCase: the frame path keeps the same kind of memory in its UseCase, the last drop reason per source, reset by `start` and `.connected` (*Effect stage* above), and the catalog's UseCase could read the problems from the entries it is handed (`availability`); but `EffectCatalogUseCaseImpl` is one process-wide value too, so its memory would outlive the run that made it, and every run would have to reset it, a second lifecycle to keep right. A memory on the Repository instance would be shared the same way, so it is a value in the stream's task instead, which lives exactly as long as the stream and needs no reset. The consequence is that a new stream, which a new run of the menu opens, logs what it finds once more. *Why full equality.* The comparison is `==` on the whole problem, so an author who edits a manifest from one invalid reason to another sees the new reason logged, and identical lines are the only thing suppressed. *Frame path.* The memory is a local value of the catalog's task, off the frame path, so no actor is added. *Not covered.* A thumbnail that cannot be used is still logged on every listing that reads it: the DataSource logs it inside the read and the package stays ready. Moving that to the Repository would need the reason carried in the listing (an Entity change), so it is the next candidate for the same rule. The folder's own errors are not deduplicated either: a folder that cannot be listed is still watched, so each change to it logs the listing error again, and one that cannot be made is logged once per catalog stream, since nothing is watched then. The suites are `EffectPackageRepositoryTests` (each transition, and ten changes to one broken package, eleven listings in all, giving one line) and `EffectPackageDataSourceTests` (a listing and repeated reads log nothing).

**Hot reload, the watch half: a directory watch on the folder and on each package, a file watch on each file, one element per burst (epic #42, D4, #46).** Owner: `EffectWatchDataSourceImpl` (a struct; port `EffectWatch`), which resolves `fileWatchGateway`, `continuousClock` and `developerLog` and nothing else, the DataSource lane of the key-path table. It decides nothing about *what* to watch: the set comes from the listing (`EffectPackageDataSource`, #45) and arming again after every listing is the Repository's (#47). *Two kinds of watch, one descriptor each.* An editor's atomic save replaces a directory entry, which a file descriptor never sees (it dies on the rename), and an in-place overwrite changes no entry, which a directory descriptor never sees. So the set carries the effects folder, each package folder and every directory that is there on the way to a package's thumbnail as directories (`watch(directory:)`), and each package's manifest, shader and thumbnail as files (`watch(file:)`): what the DataSource arms is the folder's directory watch and, per package, its directory watch, a directory watch for each directory on its thumbnail's way, and a file watch for each of its files. A path that is both is armed twice and heard twice, and still makes one burst. *Armed before the call returns.* `changes(of:)` arms every directory and then every file before it hands the stream back, so the watches are live when the call is over: the first change after a catalog the Repository has shown is buffered until someone iterates instead of lost. *An un-armable path is logged and skipped.* A path that was in the listing and is gone by the time it is armed makes the gateway throw; the DataSource records it in the developer log (`.effect`) and goes on with the rest, because a throw would cost every other watch of the set. The skip costs only that path's watch: nothing arms it again and nothing asks for a listing because of it, so the listing stays as it was until some other armed watch hears an event. *One element per burst.* Whichever watch fires restarts the same quiet period, 200 ms (`quietPeriod`) on `\.continuousClock`. Each event gets a number and a `clock.sleep` of its own, a child of a `withDiscardingTaskGroup`; when a sleep ends it reports its number, and only the report of the newest event yields an element, so a period that a later event replaced yields nothing. The watches' callbacks run on any thread and only post `.changed` to a stream of signals; one task reads that stream, together with the sleeps' reports, in order, so the counter is touched by that task alone and needs no lock. The task is the DataSource's own unstructured `Task`, as in `ExtensionInstallDataSource`: this is off the frame path, which is the `WorkRunner`'s business. *The stream never ends on its own, and its end stops every watch exactly once.* Not for an empty set and not when nothing could be armed, because `EffectPackageRepository` reads an end it did not cause as the watch being gone and ends the catalog. Only the consumer ends it (its task is cancelled, it leaves the loop, or it drops the stream), and `onTermination` then stops every armed handle once, finishes the signals and cancels the task, which cancels the sleeps still parked: the period in progress is dropped, and an event after that reaches nobody. The live handle cannot see a double stop (cancelling a cancelled `DispatchSource` does nothing), so `FakeFileWatchGateway` counts it (`isBalanced`). *Why a DataSource and not a Gateway.* `FileWatchGateway` is a thin pass-through (no branch, no timing, no loop: `scripts/check-live-thin.sh`), whereas a quiet period is time plus a decision (restart or yield) that needs a test; one layer up the clock is injected and the kernel is `FakeFileWatchGateway`. *Testing.* The suite is `Tests/EffectWatchDataSourceTests` over `FakeFileWatchGateway` and a `GatedClock`: `gateway.fire(path)` is the file system and `clock.advance(by:)` is time. A `TestClock` would not do, because an event travels from the callback through the signals stream to a sleep and nothing observable says the sleep is parked, so an `advance` made too early is lost; `GatedClock.sleepers` fires once a sleep is registered, so a test advances only when the subject is waiting on it, and `parkedCount` shows a period running out (or not) without a window of ticks. The property test replays seeded gaps drawn around the boundary (0 to 600 ms, with 199, 200 and 201 among them) against a model that writes 200 ms out itself instead of reading `quietPeriod`, so changing the constant turns it red. *Alternative not taken: FSEvents.* It is recursive (one registration for the whole folder instead of a directory watch on the folder and on each package and a file watch on each file), but it is a C API with a run loop that does not fit the thin-live rule, and its coalescing latency is the OS's, not ours to step in a test; the two-watch `DispatchSource` shape is the one lyra already proves.

**The chosen effect is kept as one string in the user's defaults (epic #42, D6).** Chain: `SettingsRepositoryImpl` → `PreferencesDataStoreImpl` → `KeyValueStoreGatewayImpl`. *Why a DataStore.* The key and the string form are persistence-shaped knowledge, neither a Gateway's thin pass-through nor a DataSource's work against a changing world, so `Preferences` is the first port under `Domain/DataStore/`; the implementation resolves `keyValueStoreGateway` and `developerLog` and nothing else (the key-path lane of a `*DataStore`). *The form.* An `EffectID` is stored as `<origin>:<key>` (`package:glitch`, `bundled:Chromatic Grain`) under the role-named key `selectedEffect`. Both are persisted, so neither is renamed, and the suite pins them literally, because a symmetric rename of encoder and decoder would still round-trip. `StoredEffectID` is the pure conversion. It cuts at the first colon (an origin never contains one, a key may) and by Unicode scalar: cut by `Character`, a key that starts with a combining mark fuses with the colon before it and no longer decodes, which the seeded round-trip property test catches. Every `EffectID` round-trips, and a string that decodes encodes back to itself. An empty key is well-formed (it cannot name a catalog entry, so the fallback of D6 covers it). *A stored string that does not decode* (no colon, an unknown or differently cased origin, a value another build wrote) is not an error: `Preferences.selectedEffect()` answers `nil`, the DataStore writes one developer-log line under `.effect` and leaves the value where it is, since a newer build may read it again, and the next choice overwrites it. Reading never writes. A relaunch then starts from the bundled default, the fallback D6 specifies for a selection the catalog does not list (`EffectCatalogUseCase`, #48). *Layers.* `SettingsRepositoryImpl` is a pass-through to `Preferences` and to the ports that joined it for the settings window (`StoreMaintenance`, `LoginItem`, `Hotkeys`), kept for the chain (`ExtensionInstallRepository`'s reason); `SettingsUseCase` exists since that window, for `SettingsInteractor`: it stamps the store's schema version (and leaves a version it does not own alone), resets every stored value, and drives launch at login and the hotkeys. *The live gateway.* `UserDefaultsGateway` is registered in `HostDependencyInjection` only. `KeyValueStoreGatewayImpl(defaults:)` takes `.standard` in the app and a UUID-named suite in the smoke, which removes the suite's persistent domain after every test. The empty `<uuid>.plist` that emptying a domain makes the OS write at process exit is out of the test's reach (a delete from the test comes back), so the smoke shares one name per run, serialized, and leaves one such file per run instead of one per test. Its smoke runs anywhere, so the module is covered and absent from `codecov.yml`'s ignore list, and the thin-live lint, which reads that list, does not look at it; it is thin all the same. The port says `removeValue(forKey:)`, which `UserDefaults` calls `removeObject`. `scripts/check-physical-symbols.sh` rejects the name `UserDefaults` in every module but `UserDefaultsGateway`, in any spelling (`UserDefaults.standard`, a call or `.init`, a type annotation, a qualified `Foundation.UserDefaults`); a comment or a string literal is not code and does not count.

**Camera choice: one pure policy resolves the state and the capture, and a remembered camera that is unplugged is not forgotten (#153, #155, #156).** Owner: `CameraSelectionPolicy` and `CameraSelectionUseCaseImpl` (`CameraControlUseCase`), `CameraSelectionRepositoryImpl`, `CameraDevices` (`CameraDataSource`), `CameraPreferences` (a DataStore) and `CameraMenuPresenter`. *One policy.* The state the menu shows and the capture the session starts are read from one `resolved` step, so the two cannot disagree: a remembered camera wins while it is connected, else the OS default camera, else the first one; a remembered resolution or frame rate the camera cannot give falls back to the M0 preset (1280×720 at 30 fps) and then to the smallest resolution or the highest rate on offer. The app's own virtual camera is left out of `CameraDevices`, since it cannot be the input of the camera it produces. *Remembering.* `refresh()` reads the stored choice and never saves it; each command saves one item of it when the state offers the new value, so unplugging the remembered camera falls back for now and its choice, format included, is back when it returns. *Keeping a chosen format.* `CaptureRig` holds the device lock from setting `activeFormat` through `startRunning()` until `stop()` (`configure` returns the release, which `stop()` calls after `stopRunning()`), because `AVCaptureSessionPresetInputPriority` is unavailable on macOS and `lockForConfiguration` is the documented way to keep a settable property from changing on its own; the preset path takes no lock, since an unneeded one degrades other apps on the same camera (#357, #539; `docs/hackathon/mvp-cd/DECISIONS.md`). Whether macOS keeps the format is checked on the device by a person.

**Stored schema version and reset: a DataStore of its own (#173, #174, #184).** Chain: `SettingsRepositoryImpl` → `StoreMaintenanceDataStoreImpl` → `KeyValueStoreGatewayImpl`. *Why a second DataStore.* The stored values carry a schema version and can all be wiped by the settings reset. The key and the form of the version are persistence-shaped knowledge like `Preferences`' keys, but they belong to no one setting, so `StoreMaintenance` is its own port under `Domain/DataStore/` and `Preferences` does not grow a second reason to change; `SettingsRepository` passes the three calls through unchanged. *The form.* The version is a decimal string under the persisted key `storeSchemaVersion`, never renamed, and the suite pins key and form literally. `schemaVersion()` answers `.missing` when nothing was stamped, `.version(n)` for an integer of 1 or more and `.unreadable` for anything else (`abc`, `0`, `-2`, empty): one developer-log line, the value left where it is, since another build may have written it and may read it again; reading never writes, the same rule as the chosen effect's. *Reset.* `resetAll()` is one `KeyValueStoreGateway.removeAll()` and one developer-log line, `store reset`: it removes every value the app stored, the chosen effect and the version included, and does not stamp again. *Where the policy lives.* What to do with a version is the UseCase's: `SettingsUseCase.prepareStore` stamps a missing or older version and leaves a newer or unreadable one alone, and `resetAll` clears the store and stamps the current version again (#184), so the DataStore holds no migration logic. `StoreMaintenanceDataStore` is registered in `HostDependencyInjection` only.

**Effect catalog: the UseCase selects and reloads; the pipeline never learns (epic #42, D5 / D6 / D11).** Owner: `EffectCatalogUseCase` (`EffectCatalogUseCaseImpl`), the only caller of `EffectRuntimeRepository.prepare`. *Hot reload is `prepare` again.* The Repository lists the catalog again after every change (a new package, a gone one, an edited file), so an edit arrives as a listing: for the chosen effect the UseCase reads `source(of:)` and, when the `EffectSource` differs from the last one it handed the runtime, prepares it (the first listing of a run always differs). A source that does not compile is `.compileFailed` and the pipeline passes frames through, MVP-A's rule unchanged; fixing the file prepares it again and brings the effect back. *There is no last-good library to keep:* it would collide with the runtime's selection rule (the newest `prepare` decides, success or failure) and hide the failure, while the pass-through is the shortest signal to an author that the edit broke the effect. *Fallback and restore (D6).* A run starts by reading the persisted choice, and each listing settles it: kept when the listing has it ready, otherwise the first bundled entry — a first start, a package that went away, or one whose files are broken. The bundled effect is taken from the listing because `bundledEffects` is a DataSource port, which a UseCase does not resolve. A fallback is logged and is not written back: only `select` writes the settings, so the persisted choice stays the user's last explicit one and comes back at the next launch if its package has. A listing without a bundled entry has nothing to fall back on and publishes nothing. *One state, published whenever it changes.* A listing that needs a `prepare` publishes after the runtime has answered, with the outcome; one that needs none publishes at once, carrying what the last attempt has answered so far (the outcome is `nil` while that attempt is still out, or has not begun because a choice is made before its `prepare` is issued and an answer for the effect chosen before can arrive in between, so the menu can show the chosen row before its outcome); a state equal to the last one is not published, so a hot reload that works, which changes nothing the menu shows, publishes nothing (the next listing is what proves it landed). `select` of a broken or unknown id answers `.unavailable` and changes and calls nothing; choosing the chosen effect again prepares it again, which is the retry after a runtime `.internalError`. A chosen package that is listed ready but whose source cannot be read just then is chosen and remembered all the same, is logged, and shows `.unavailable(problem)` as the outcome (the `select` that met it answers the same); the runtime keeps what it has, and a `prepare` still out goes on, its answer kept behind the problem rather than dropped. The next listing that reads the source again brings the answer back: the runtime's own when it already has that very source (nothing is prepared again), a fresh `prepare` for a new one. A `select` overtaken while it was remembered or while it read its source (by another choice, the catalog losing the package, a newer read of the same effect's source, or a new run) answers `.unavailable(nil)` and prepares nothing; the same two guards, a run number and a read number, keep a listing's stale read from preparing over a newer one. *Newest wins is mirrored, not re-implemented.* The runtime keeps the effect of its newest `prepare`, so the menu must show the newest request's outcome. The decisions are in one actor, `EffectCatalogSession` — low-rate and off the frame path, so an actor is allowed, and nothing in it touches a surface. Its `generation` is bumped in the same actor turn that calls `prepare`, with no suspension between, so its order is the runtime's; an answer that comes back after a newer `prepare` still reaches its own caller but publishes nothing, which the suites prove by completing the runtime fake's prepares in both orders. Before issuing anything, each flow re-checks that the effect it read the source of is still the chosen one, so a `select` that arrives while a listing waits for a source (or the reverse) leaves the effect to the newest choice. *Observers.* `observe()` is synchronous in the port, which an actor cannot be, so the states go through a `CurrentValueSubject` (`EffectCatalogBroadcast`): a stream is subscribed while it is built, before `observe()` returns, so a state published right after is never missed, the current state arrives at once and any number of observers see the same sequence. The lock the UseCases are denied is the subject's own, and every `send` comes from the one actor. The subjects are never completed: a run that ends (its task cancelled) ends the streams opened so far, lets go of the catalog and forgets the state and the last-prepared source, so a later run restores the choice and prepares again. A stream opened in the very instant a run ends may be handed that run's last state or miss the end, because its two subscriptions and the run's two steps of ending are not one step and a lock is not available here; the port asks callers not to open one then, and the Interactor opens its stream as its run begins, after the run before has returned. *What it relies on:* `EffectPackageRepository.catalog()` listing again after every change, an identical entries array included, since a shader edit changes no row.

**The effects menu's Interactor and Presenter (epic #42, D9).** Owner: `EffectInteractorImpl` (`EffectInteractor`) and `MenuBarPresenter` (`Presenters`). The Interactor owns the one task that runs the catalog: `start()` runs `EffectCatalogUseCase.run()` and the forwarding of `observe()` into a `CurrentValueSubject` as the two children of one task, so cancelling the task reaches both, and `state` is that subject without its `nil` — empty before the first `start()`, the latest state for every later subscriber. `start()` and `stop()` are synchronous on the port, so each only queues a command on an `AsyncStream`; one supervising task, started when the Interactor is made, carries the commands out one at a time, in call order: it cancels the run that is alive, waits for it, and begins the next on `start`. That is how the task handle needs neither a lock (the physical-symbol lint bans `NSLock` and `OSAllocatedUnfairLock` above the Gateway) nor an actor hop that could reorder `start(); stop()` (an unstructured `Task { await actor.start() }` per call could); waiting for the old run before the new one begins is what keeps a stale state from landing after a fresh one. A second `start()` therefore restarts the catalog, as the port says, and a released Interactor ends the run it owned. `select(_:)` returns nothing on the port, so it spawns a task for the UseCase's answer and writes one log line (`DeveloperLog` for `.prepared`, `ErrorLog` for a failed or unavailable effect); the outcome reaches the menu through `state`. It is deliberately not one of the queued commands, and it does not wait for an earlier `select` either: the runtime's newest-wins (*Effect runtime* above) is built so that a newer `prepare` overtakes a slow compile, and a queue here would hold the newer choice back behind the older one's compile. The price is that two `select`s made in the same instant may reach the UseCase in either order, which a person choosing from a menu does not produce; the port documents it, and a caller that needs an order waits for the first outcome in `state`. `MenuBarPresenter` is `@MainActor`; a `sink` hands every state to an `AsyncStream` that keeps the newest (`bufferingNewest(1)`), and a main-actor task applies them. It is neither `receive(on: DispatchQueue.main)` (the physical-symbol lint bans the queue, and a test would have to poll for the hop) nor a task over `interactor.state.values`: an `AsyncPublisher` asks for one value at a time, and a state sent while the task is still applying the previous one is dropped (a producer on another thread sending 100,000 states at a main-actor consumer that did a little work for each saw fewer than 2,000 of them arrive), which could leave the menu on a state that is no longer the catalog's. The `sink` takes unlimited demand, and the stream keeps the last state until the task has applied it. `stop()` ends the observation by cancelling the subscription and the task and finishing the stream, and the loop checks the cancellation before it applies a state: an `AsyncStream` still delivers a value it had already handed to its consumer, so without the check a state sent just before `stop()` would change the rows after it. Its suite waits with `settle` on `$items` / `$status` alone. It owns the Interactor's lifecycle for the menu (and, since the bypass and the frame-rate readout joined the menu, `ControlsInteractor`'s too: *The controls, settings, onboarding and authoring Interactors* below) — `start()` observes and then starts the Interactor, `stop()` ends both, and a started Presenter that is let go does what `stop()` does (its observation task and the Interactor's run would otherwise outlive it) — because the Router above it resolves no Interactor and may not skip a layer; the Router decides when to call them, and nothing starts in `init`. The Presenter's `start()` / `stop()` are therefore the only calls that begin and end the menu: whoever wires it (the Router, which the host's and the dev harness's delegates start) calls them and never `effectInteractor.start()` itself, because a second `start()` is a restart, so the catalog's `run()` would run twice at launch and the first state would be sent twice. `scripts/check-dependency-keypaths.sh` keeps the entry points to it: `App` and `DevHarness` are denied `\.effectInteractor` (*Menu bar* below). Display data follows the layer rules: `EffectMenuItem` is pure data in `Entity`, the wording of a package problem or a failure (`"<name>: compile failed"`) is a pure function inside `Presenters`, and `EffectCatalogEntry` carries the manifest's `author` so that the Presenter can show it (the Repository that assembles the catalog fills it, #47). Alternatives not taken: an `actor` holding the task (reorders unless every call goes through a mailbox anyway, which is this design with an extra type), a lock-protected task slot (banned above the Gateway), and a Presenter that subscribes in `init` (a constructor with a side effect, and the Router could not choose when the catalog starts).

**Effect picker: a second view of the menu's state, opened by the Router (#12).** Owner: `EffectPickerPresenter` and `resolveArtwork` (`Presenters`), `EffectPickerView` (`Views`), and `AppRouter` with its `EffectPickerWindow` and `EffectThumbnailDecoding`. *One state, two views.* The picker is a window with one cell per catalog entry, over the same `EffectInteractor.state` the menu draws: the chosen cell is the menu's checked row because both come from the one state's `selection`, not because one view tells the other, and a cell is enabled exactly when its row is. Choosing a cell is `EffectInteractor.select`, as choosing a row is. The wording is shared, not repeated: a cell's second line is the row's (`MenuBarText.detail(of:)`), the status line above the grid is the menu's (`MenuBarText.status(of:)`), and the hover help says what the cell abbreviates: the name with its author and, on a line after them, the manifest's `description` (without the whitespace around it, cut at 280 Unicode scalars with an ellipsis when something other than whitespace follows the cut within the next 280 scalars, and left out when blank; the cap bounds the description alone, in scalars and not in `Character`s, so a thousand combining marks on one letter do not slip through, and the Presenter reads, on each keystroke, the whitespace before the text, the text up to the cut and 280 scalars past it, not a long description through (a gap of more than 280 whitespace scalars after the cut hides what follows it without an ellipsis); the name and the author are not cut, the cell shows them in full too), or for a broken package `<name> cannot be chosen: <reason>`. *The description rides on the catalog entry.* `EffectCatalogEntry.description` is the manifest's, as written, for a ready package (`nil` for the bundled effect and a broken package), filled by `EffectPackageRepositoryImpl` where the manifest is in hand, so no DataSource or UseCase changes; a listing that changes only a description is a new catalog and a new state, like one that changes only a picture. *It only observes.* The menu's Presenter owns the Interactor's run (*The effects menu's Interactor and Presenter* above), and a second `start()` is a restart, so `EffectPickerPresenter.start()` subscribes to `state` and does nothing else, and `stop()` lets go of it and clears the search; `state` replays the latest value, so a picker opened late shows the catalog at once. The observation is the menu's own code, shared rather than copied (`CatalogStateObservation`: a `sink` into a newest-wins `AsyncStream` that a main-actor task applies, the cancellation checked before each apply). *Search is the Presenter's.* The query, without the whitespace around it, is matched against the name or the author, ignoring case, diacritics and full- or half-width forms, under no locale, so it finds the same cells on every machine; a search that hides every effect shows `No effects match “<search>”`. *Layout is logic, so it is not in `Views`.* `EffectPickerGeometry(width:)` gives the column count (as many cells of the minimum width as fit between the insets, from 1 to 32) and the cell width that fills the row; a width that is negative or not finite is one column with no room. `Views` is coverage-ignored and holds declarations only, so the geometry is a pure type in `Presenters`, tested by examples and a seeded property test, and the View hands it the width a `GeometryReader` reports. *Thumbnails: the picture when there is one, the tile when there is none or when the picture does not decode.* A cell's `artwork` is `EffectArtwork`: either `.placeholder(EffectPlaceholder)`, a monogram (the first letter or digit of each of the first two words of the name, upper-cased) on a gradient whose hue comes from a 64-bit FNV-1a hash of `<origin>:<key>`, so an effect keeps its colour across launches and processes, which `hashValue` would not; or `.image(EffectThumbnail, fallback: EffectPlaceholder)`, which the Presenter chooses exactly when the entry is a package that can be chosen and carries a thumbnail (the bundled effect, a package whose manifest names none or names one that cannot be used, and a broken package carry none, and a broken one gets the tile whatever its entry carries, as it gets no description in its hover). The image case holds the effect's own tile as well, because its bytes passed only the package DataSource's checks (size and signature) and a decode can still fail. *The decision that a failed decode is the tile lives in `Presenters`.* `resolveArtwork(_:decode:)` is a pure function, generic over the decoded image: it hands a thumbnail to the `decode` closure it is given and answers the image, or the artwork's fallback tile when the closure answers `nil`, and it never decodes a placeholder. `Views` is coverage-ignored and holds declarations only, so the decision cannot sit in `EffectArtworkView`, which only maps the answer to pixels (a filled, clipped image or the gradient tile); `EffectArtworkResolutionTests` pin it over stub decoders that succeed and fail. *The live decoder is the Router's.* `EffectThumbnailDecoding` (`AppRouter`, AppKit; `EffectPickerWindow` hands it to the view, which passes it down as a closure to `EffectArtworkView`) makes a `CGImage` of the bytes with `NSBitmapImageRep(data:)` and not `NSImage(data:)`, which answers an image of no size for bytes that carry only a signature and would draw an empty cell; the call is `nil` for those, for a header cut off before the pixel data begins, for a PNG that says it has no pixels and for no bytes at all, and `EffectThumbnailDecodingTests` run it over real PNG and JPEG bytes, over a solid colour (which must come back as that colour), over `Examples/Ripple.lens/thumbnail.png` (256 × 256, RGB: the picture the README ships) and over a hand-made zero-size PNG. *It does not check that a picture is complete.* A PNG or a JPEG cut off inside its pixel data decodes to an image of the header's size, the rows it never got drawn black (PNG) or grey (JPEG), and ImageIO still calls the source complete; that was observed on the machine this was written on, it is the OS's, and no test holds a build to it. So a file that is half written draws half a picture until the watch reads the finished one, and a file left cut off draws that way. Telling it by its end would be sound for a PNG (`IEND` is the last chunk) and not for a JPEG (a file may carry bytes after its end marker, and one without its last bytes still decodes), so it is not done. The call also refuses a picture of more than 2048 × 2048 pixels in all (pixels, not points and not a side: 4096 × 1024 is within it, and 2049 × 2049 pixels is over it however many points it says it is), which the DataSource's byte limit does not prevent: a PNG within 1 MiB can claim tens of thousands of pixels on a side (a 15 000 × 15 000 grey PNG of 982 742 bytes opened in about a millisecond with no measurable memory, and drawing it added about 226 MB and took 0.34 s, measured on the machine this was written on), so a larger picture is the tile. Refusing it after `NSBitmapImageRep(data:)` has read the header costs nothing because the OS decodes lazily, which is its behaviour and not a documented promise; the limit is what bounds what is drawn if that ever changes. A picture that does not decode, or is over the limit, is not logged: nothing below the view lane knows it, and the tile is the only sign. *Known limits.* The decode runs where the view's body runs, on the main actor, and is not cached. How often that is was counted, with a counter in place of the decoder and the picker's view in an offscreen `NSHostingView` over nine picture cells and two tile cells: the first render decoded nine times (once per picture cell, none for a tile), a second identical pass none, a search that changed which cells are shown three times, the next, narrower search none, and a wider window none. That fits SwiftUI skipping the body of an `EffectArtworkView` whose `artwork` and `decode` are unchanged, the one `decode` closure being the same on every pass: a keystroke or a resize does not decode the cells that stay. A picture is decoded again when its cell is built again, when it scrolls out of the `LazyVGrid` and back or when its bytes change. A picture within the limit is not downsampled to the cell, so while it is drawn it costs up to 16 MB (2048 × 2048 at 4 bytes a pixel) per visible cell, where the README asks for 512 × 512 (1 MiB): the worst case is every cell the window shows at the limit, each time its cell is built. *Alternatives not taken:* the resolver in `Views` (an untested branch in a coverage-ignored module, which `.claude/rules/coverage-ignored-modules.md` forbids), a decoder port with its own Gateway (a module, a fake, a DI entry and a lint row for one expression), `NSImage(data:)` (above), and ImageIO's thumbnail call, which would read the size from the header and bound the memory by downsampling. That one is a choice and not a rule: the lane's import list could take ImageIO (a word in `scripts/check-imports.sh` and a row of `.claude/rules/architecture-boundaries.md`). It is not taken because the count above shows the decode is not repeated per pass, `NSBitmapImageRep` is what was checked by eye on a render, and a downsample or a cache is a second code path or state to keep right for a cost that has not been seen; it is the next step if a catalog of large pictures makes the picker slow. *The Router opens and closes it.* `AppRouter` is the menu's `MenuBarRouting`: *Browse Effects…* goes from the View to `MenuBarPresenter.browseEffects()` and on to the Router, which the Presenter holds weak because the Router owns it. The Router makes the window through `makePickerWindow` (`PickerWindowFactory`; the default builds `EffectPickerWindow`, which hosts `EffectPickerView` in an `NSWindow`), keeps at most one (asking again brings it to the front), starts the picker's Presenter while it is open, and lets go of both when it closes. The window reports its own close, with itself, whether its title bar or the Router closed it; the Router compares it with the window it holds, so a report from a window it has already let go changes nothing. `stop()` closes the picker before it stops the menu. The window's AppKit glue, `EffectPickerWindow`, lives in `AppRouter` beside the Router rather than in `Views`, which is coverage-ignored and holds declarations only; the Router itself sees it only through the `PickerWindow` protocol, and `AppRouter` imports `Views` for the `EffectPickerView` the window hosts (`scripts/check-imports.sh`). The host's `HostAppDelegate` keeps the app running when the host's last window (the picker, the settings window, the parameter panel or the onboarding window) closes; the dev harness quits when its preview window closes, the picker open or not, and it shows the item too, since its Effects menu is the host's `EffectMenu`. *Tested, and not.* `EffectPickerPresenterTests` drive the Presenter over a fake Interactor: the cells, their flags and words (the hover with and without a description, a blank one, a long one and a broken package's), their artwork (a picture in either format with its own tile to fall back on, none, a broken package, a picture replaced or removed), the search, the chosen cell following the menu's checked row through every change of choice with both Presenters over one Interactor, and an Interactor the picker never starts or stops. `AppRouterPickerTests` drive the Router over fake windows: one window, the same one brought forward, a title-bar close, a stale close, `stop()`, and a Router let go with the picker open; one test makes the live `EffectPickerWindow` to check that its close reports itself, without showing it. `EffectArtworkResolutionTests` and `EffectThumbnailDecodingTests` are above. View bodies are not unit-tested, and what a person sees is checked by eye on a device (the *Effect picker* row of Lane 1 in `.claude/rules/dev-verification.md` lists what to look at; it has not been run on a device, and the appearance of a picture has no automated coverage). *The live preview (#68).* A pane above the grid shows the camera through the chosen effect, with a control that splits it against the unprocessed frame: `PreviewPaneView` over a `PreviewPresenter` that `AppRouter` builds for the host only (`showsPreview`) and starts and stops with the picker window, attaching the pane's view to the pipeline only while the picker is open and visible (*Preview pane in the picker* below). Alternatives not taken: a picker Presenter that starts the Interactor (the catalog would restart each time the window opens), a picker that reads the menu's Presenter (a Presenter depending on a Presenter, and no picker without the menu), and the geometry in `Views` (untested logic in a coverage-ignored module).

**The controls, settings, onboarding and authoring Interactors: commands queue, one task carries them out, the state is what the UseCase reads back (#188, #189, #191, #216, #217, #274).** Owner: `ControlsInteractorImpl`, `SettingsInteractorImpl`, `OnboardingInteractorImpl` and `EffectAuthoringInteractorImpl`, one target each, registered in `HostDependencyInjection` only, since the extension process has no GUI and so no Interactor lane. *The shape is `EffectInteractorImpl`'s* (*The effects menu's Interactor and Presenter* above): the three that hold state make an `AsyncStream` of commands and one supervising task when they are made, their synchronous port methods only `yield` a command, the task carries the commands out one at a time in call order, and `deinit` finishes the stream so that the task, which holds the UseCases and never the Interactor, ends with it; the state is a `CurrentValueSubject` behind a private relay. So there is no lock (the lint bans it above the Gateway) and no actor hop that could reorder two commands. *Where they differ.* `SettingsInteractorImpl` publishes after every command what `SettingsUseCase.settings()` reads back, so the published state is the UseCase's and never the Interactor's guess; `resetAll()` is its one async command, which parks the caller on a continuation that the supervisor resumes after the reset's publish (at once when the command could not be queued), so a command queued during a reset waits for it. `OnboardingInteractorImpl` ends the observation that is alive on every command and waits for it before the next begins, as the effects menu's Interactor does, so a status of the old observation never lands after the new one began; `openApprovalSettings` and `exportSupportLog` are not queued, because neither begins nor ends the observation, and each awaits its UseCase and returns the answer as it is. `ControlsInteractorImpl` has two feeders into its queue besides the port's commands, a one-second sampler on `\.continuousClock` and the hotkey listener, and both only `yield` into that queue, so a sample, a press and a toggle reach `state` and the pipeline in one order; a sample or a press that reaches the queue after a `stop()` was carried out is dropped, so nothing is published after it. A next / previous press is not a queued command: it asks `EffectCatalogUseCase.selectAdjacent` in a task of its own, so the queue never waits for a compile (as `EffectInteractor.select` does not), and logs the outcome in one line (developer log for `.prepared` and for `nil`, the normal end of the list; error log for a failure or an unavailable effect). The switch goes through the UseCase because an Interactor may not resolve another (the Interactor lane of the key-path table is UseCases and Support), and the hotkeys are registered through `SettingsUseCase` (`prepareStore()`, then `hotkeyPresses()`, then `applyHotkeys()`, with the presses stream opened before the registration so no press is lost): `stop()` ends the listener and leaves the registration, and the next `start()` opens the presses again. `EffectAuthoringInteractorImpl` is the exception: no queue, no task, no state and no publisher, because the command-line tool makes one call and shows the answer; it is a stateless struct that answers what `EffectAuthoringUseCase` answers, unchanged, and leaves one developer-log line (`.effect`) per call and none in the error log, because the tool prints the failure itself. The entry lane may resolve Interactors, so `LensTool` resolves `\.effectAuthoringInteractor` as `DevHarness` resolves `\.harnessInteractor`, and never the UseCase beneath it. None of the four needs a per-key exception in the key-path lint: each resolves UseCase and Support ports only. *Who starts them.* `MenuBarPresenter.start()` / `stop()` begin and end the controls beside the effects Interactor and forward the bypass toggle, `OnboardingPresenter` begins and ends the install observation, and `SettingsPresenter` calls `refresh()` when it starts; no entry point starts one. *Live resolution.* `HarnessLiveWiringTests` resolves the controls and settings Interactors live, inside the harness's discarding-sink substitution (the controls Interactor resolves the frame pipeline, which keeps the sink of the scope that builds it); `scripts/check-live-owner.sh` still names only `\.effectInteractor` and `\.effectCatalogUseCase`. Alternatives not taken: calling `EffectInteractor` from the hotkey listener (Interactor → Interactor, #189), and a Combine publisher on the authoring Interactor (its call is one-shot and keeps no state to publish, #274).

**Onboarding window: a status the window only observes, and two actions (#215, #217, #225–#227, #230, #232).** Owner: `OnboardingPresenter` and `OnboardingText` (`Presenters`), `OnboardingRouter` and `OnboardingWindow` (`AppRouter`), `OnboardingInteractor`, `ExtensionInstallUseCase` and `SupportLogUseCase`. *Observe, never drive.* The window shows the virtual camera's install status (`ExtensionInstallUseCase.updates()`, forwarded by one supervised task in `OnboardingInteractor` into an `install` publisher that keeps the latest status for a late subscriber) and has two actions, opening System Settings for the approval and exporting the support log. **Support log: this process's lines, bound with the environment, saved as one file (#211, #212, #213, #214, #215, #217).** Chain: `OnboardingInteractorImpl.exportSupportLog` → `SupportLogUseCaseImpl` → `SupportLogRepositoryImpl` → `SupportLogDataSourceImpl` → `LogStoreGatewayImpl`, all registered in `HostDependencyInjection` only (the extension links none of them). *Scope of the read.* `LogStoreGatewayImpl` opens `OSLogStore(scope: .currentProcessIdentifier)`, which holds the host process's lines and not the Camera Extension's, so a report says nothing about the extension's own log. `UnifiedLogImpl` writes `ErrorLog` at `.error` and `DeveloperLog` at `.debug`, which the OS discards unless a debugger or `log config` asks for it, so the store holds mostly error lines. The Gateway filters nothing (no level, no sort, no page: each would be a branch in a coverage-ignored module) and takes the subsystem as an argument instead of reading `ProductIdentity.logSubsystem`. *Which layer decides what.* The order, the cap and the file are persistence-shaped knowledge, so they are `SupportLogDataSourceImpl`'s: the lines sorted by timestamp with the read position as the second key (equal timestamps keep the order they were read in without relying on `sorted` being stable), the newest 500, and `save`, which makes the `Diagnostics` folder (`AppDirectoriesProvider.diagnosticsDirectory`, a sibling of the effects folder), writes `support-log.txt` there, opens the folder through `WorkspaceGateway` and logs one developer line; a folder that cannot be made or a file that cannot be written throws and Finder stays closed. The report's wording is the UseCase's, as a pure function (`supportReportText`: the display name, the app and macOS versions, the Camera Extension's install status, the effect's status, the compiler's output cut at 4000 characters, then the lines as `<ISO 8601 time> [<category>] <message>`). *An unreadable log does not stop the report.* `SupportLogRepository.snapshot()` never throws: when the store cannot be read, `entries` is empty and `logError` carries the reason, and the report says so beside the versions and the install status. *A failure is a value.* `SupportLogUseCase.export` never throws: it answers `.saved(path:lineCount:logError:)` or `.failed(description:)`, with an error-log line for a failed save and a developer line for a saved one, and `OnboardingPresenter` shows the outcome; the call does synchronous I/O under an `async` signature, so a caller runs it from a `Task`. *Tests.* `LogStoreGateway` is the only module `scripts/check-imports.sh` lets import `OSLog`; it is coverage-ignored, thin and has no smoke suite, because a log store cannot be read in CI, so only a person on a device sees real lines. The layers above run on `FakeLogStoreGateway`, `FakeSupportLogs` and `FakeSupportLogRepository`.

**IOSurface → `MTLTexture` by `makeTexture(descriptor:iosurface:plane:)`, not `CVMetalTextureCache`.** Frames are already IOSurfaces — there is no `CVPixelBuffer` to feed a texture cache — so `TextureCacheGateway.bind` wraps plane 0 directly: `bgra8Unorm`, `.shared` storage (the product targets Apple silicon only), `shaderRead | shaderWrite`. A thin live cannot branch on the device, so the storage mode is hardcoded; the #15 spike ran the same compute fill through `.shared` and `.managed` textures on Apple silicon, and the `test-gpu` job re-proves `.shared` on the runner's paravirtual device on every PR. The surface's rows must be 16-byte aligned or Metal aborts the process inside `makeTexture` (validation layer or not), and IOSurface keeps an explicit `bytesPerRow` exactly as given — `width * 4` for a 6-pixel-wide surface stays 24 — so the alignment belongs to allocation, not to binding: `IOSurfaceGateway.create` passes the request through `IOSurfaceAlignProperty` (one OS call, no branch, so the gateway stays thin) and every surface it makes is bindable, slate included. Aligning in `SurfacePoolDataSource` instead would need the alignment hardcoded above the OS boundary or a second port call every allocation path must remember (#32). Dispatch is `dispatchThreadgroups` only: whole threadgroups work on every family, `DispatchGrid.covering` rounds the grid up and every kernel bounds-checks its `gid`. The compile handle (`LibraryHandle`) is the entry kernel's `MTLComputePipelineState`, built once in `compile` and cached by `EffectRuntimeStateDataSource`, never per frame; the pass (`ComputePass`) carries handles, so it is declared in `Domain` next to them rather than in `Entity`.

**`fastMathEnabled`, not `mathMode`.** `ShaderCompileOptions.precise` is the port's vocabulary; the live sets `MTLCompileOptions.fastMathEnabled = !precise` and nothing else. `mathMode` needs macOS 15, and `languageVersion` / `#available` would be a branch in a thin live. The deployment target is 14, where `fastMathEnabled` is not yet deprecated, so the build stays warning-free.

**No Metal in the extension process.** `MetalGateway` and `MetalKitPreviewGateway` are linked by `HostDependencyInjection` only. `scripts/check-extension-no-metal.sh` (in `make check`) walks `swift package dump-package` from `ExtensionApp` and `ExtensionDependencyInjection` and fails when either reaches a Metal module, `PreviewDataSource` (it carries the preview kernel's MSL) or `Views` (it imports MetalKit).

**Preview: one compute blit into the view's layer.** The preview reuses the effect path's own vocabulary instead of adding a render pipeline: `PreviewDataSource` compiles one kernel (`previewBlit`: aspect-fit, bilinear, black bars, bounds-checked `gid`) through `ShaderLibraryGateway` into the same `LibraryHandle` (a compute pipeline state), and `PreviewGateway.draw` dispatches it with the frame's texture at index 0 and the drawable's texture at index 1; the before/after split is a second kernel (`previewSplit`: the original left of a two-pixel white rule, the frame right, the original's texture at index 2) of its own source and options, so the blit's text and compile key do not change. That needs `framebufferOnly = false` on the view, which `prepare` sets with the device, `bgra8Unorm`, and a paused draw loop (`isPaused`, no `setNeedsDisplay`): frames, not the display link, drive the preview. A paused `MTKView` stops sizing its layer — it updates its own `drawableSize` on a resize or a scale change, but the layer keeps the size of its first drawable — so `prepare` also sets the view's delegate to a forwarder that copies every `drawableSizeWillChange` onto the layer; the layer handle holds the forwarder (the view holds its delegate weakly), and `PreviewSmokeTests` resizes a view between two draws to pin it. The drawable comes from `CAMetalLayer.nextDrawable()`, not `MTKView.currentDrawable` — the latter is cached until the view's own `draw` and is a main-thread API, while `nextDrawable` may be called from the frame executor. Readying the view is main-thread work, so `attach` is `@MainActor` all the way down (`PreviewSink`, `PreviewRenderer`, `PreviewGateway.prepare`); `attach` makes a GPU context, readies the view and then hands the layer to the frame executor, where it compiles the kernel once per attach — never per frame — and the split kernel right after it on the same context. A failed blit compile detaches (frames complete at once) and is logged; a failed split compile keeps the attach, is logged, and every frame is drawn as the blit; a refused attach leaves the previous view attached. One draw is in flight at a time and the latest frame wins: a frame that arrives while a draw is pending replaces the waiting one, and the replaced frame completes at once, so every presented frame completes exactly once and the pipeline's in-flight cap is never held by the preview. GPU errors are logged under `LogSubsystem.preview` and the frame still completes. Trade-off: `nextDrawable` can block up to one second on the frame executor when the compositor holds every drawable (e.g. an occluded window); measuring that on a device is Lane 1's job, and moving the wait off the executor is the fallback. The harness makes it observable: the pipeline's ticks share the executor, so its once-a-second `pipeline` summary line drifts apart in `log stream` timestamps while a draw blocks (`.claude/rules/dev-verification.md` Lane 1).

**Preview pane in the picker, and a before/after split that lends the pass's input (#242, #245, #250, #255).** Owner: `PreviewPresenter` (`Presenters`), `PreviewPaneView` and `PreviewView` (`Views`) and `AppRouter`, over `PreviewInteractor` and the pipeline's `PreviewSink`. *Where it lives.* The pane sits above the picker's grid. `AppRouter` builds its one `PreviewPresenter` only for the host (`showsPreview`; the dev harness keeps attaching its own `PreviewView` through `HarnessInteractor`) and starts and stops it with the picker window. The Presenter attaches the pane's view to the pipeline only while three facts hold, the picker is open, its window is visible and the pane's view exists, and detaches at once when any of them ends, so a closed or hidden picker costs the pipeline nothing; a refused attach (`PreviewRefusal`: no device, a foreign target, or another failure) becomes the words the pane shows in place of the picture. *The split.* A segmented control chooses `After` (the default) or `Split`, and closing the picker puts it back to `After`. In `Split` the pipeline hands a successful pass's input to `PreviewSink.present(_:original:completion:)` as the frame's original, and `PreviewDataSource` draws both with the second kernel, `previewSplit`, compiled after the blit on the same context; a split kernel that does not compile keeps the attach, is logged, and every frame is drawn as the blit. *Leases.* The original is the pass's own input, lent and not copied: `completion` ends both leases, exactly once, drawn or not, and the pipeline releases the input then instead of at the runtime's answer; the virtual camera never sees the original. The in-flight cap still ends at the answer (*Preview fan-out* above), so a slow preview costs pool surfaces and never a frame.

**Offline authoring: a command-line tool over the host graph, one still image through the existing runtime (#264, #273, #277).** Owner: `LensToolMain` (`LensTool`), `EffectAuthoringInteractorImpl`, `EffectAuthoringUseCaseImpl` and `StandardStreamsImpl`. *The entry only reads arguments.* `main.swift` runs `exit(await LensToolMain().run(arguments))` with the arguments after the program name, and `import HostDependencyInjection` is what links the live registrations, as in the dev harness. `LensToolArguments` (pure) reads the arguments into an Entity `LensCommand` (`validate`, `scaffold`, `render`, `help`) or a `LensUsageProblem`; every word printed is `AuthoringReportText` (`Presenters`, pure); `LensToolMain` only chooses the stream and the exit code: 0 for a command that succeeds and for `help`, 1 for a command that fails (a bad package or image is a failure, not a usage error), 2 for a usage error (no command, an unknown command, a missing value, an unexpected argument, an unknown or repeated option: every `LensUsageProblem`). **Still images: refused before they are decoded, every failure a value (#263, #265, #266).** Owner: `StillImageDataSourceImpl` (a struct; `maxFileBytes`, 64 MiB, and `maxSide`, 4096, are `init` parameters, so a test passes small ones). Chain: `EffectAuthoringUseCaseImpl` → `StillImageRepositoryImpl` (a pass-through) → `StillImageDataSourceImpl` → `FileSystemGatewayImpl` for the bytes and `ImageIOGatewayImpl` for the picture. *Why before decoding.* A decoded image of 4096 × 4096 is 64 MiB of BGRA, so `read` asks `readData(_:upTo:)` for `maxFileBytes + 1` bytes and decides `.tooLarge(limit:)` on the count (a larger file is never held whole; one of exactly `maxFileBytes` is read on), then reads the size from the header with `dimensions(of:)` and answers `.dimensionsOutOfRange` for a side outside `1...maxSide` before any pixel is decoded. *Why values.* Every failure is a case of the closed `StillImageProblem` (`unreadable`, `tooLarge`, `notAnImage`, `dimensionsOutOfRange`, `unwritable`) and is never thrown, because the authoring command reports the reason and every consumer enumerates it; the gateway says only which of its two failures it met (`ImageIOError.notAnImage` or `.encodeFailed`) and the DataSource gives it the path. `write` encodes to PNG and writes it, and does not make the parent directory: a missing one is `.unwritable`. *One pixel layout.* `StillImage` is the form the frame path takes (8 bit sRGB, premultiplied BGRA, rows packed) and `ImageIOGatewayImpl.bitmapInfo` is the one place that says so; `decode` draws into an sRGB `CGContext`, so a PNG in another color space is converted, and copies the pixels inside `withExtendedLifetime(context)`, because Swift may release the context after its last use and the copied pointer would then dangle. *Coverage.* `ImageIOGateway` needs no GPU and no window, so it is not coverage-ignored: `ImageIOGatewayTests` runs the real calls (the header read, the layout, the PNG signature, the round trip) and `LensToolRenderSmokeTests` runs the whole chain in `make test-gpu`.

**View gallery: a window is checked by pixels over fixture Interactors, not through the camera (#86, #87, #97).** Owner: `ViewGallery` (`GalleryCommand`, `GalleryScreen`, `galleryScreens`, `GalleryAppDelegate`) and `scripts/gallery`. *Why it exists.* `Views` is not unit-tested and the dev harness raises a modal camera prompt, so a worker could not look at the window it built; the gallery opens one window over fixture data and `scripts/gallery <screen> <out.png>` photographs it. *No live graph, nothing resolved.* The module links `AppRouter`, `Views` and `Presenters`, neither `HostDependencyInjection` nor `TestDoubles`, and has no `@Dependency` (its lane in the key-path lint is the default, none): each screen builds its `AppRouter` inside `withDependencies`, because the Presenters capture the dependencies of the scope they are built in, and assigns fixture Interactors (`Fixtures/`: each publishes the one state it was made with and its commands do nothing, since a screen shows a state and does not move it). **Untrusted shaders: contain, detect, disable.** A community shader cannot run CPU code but can hang the GPU (`timeout`), fault (`pageFault`) and, repeated, get the process's Metal access revoked (`accessRevoked`); Metal offers no execution-time limit or abort. Policy: one command buffer per effect, `errorOptions = .encoderExecutionStatus` to attribute faults, pass-through on failure, and, pure in `EffectHealthPolicy` (`EffectCatalogUseCase`), a `gpuStart/gpuEnd` budget and auto-disable after k consecutive failures with a cool-down and one trial pass, the disabled set persisted (*Effect health* below). Tests synthesize raw error codes; real hangs are a manual VM lane only.

**One effect, one command buffer; the outcome is interpreted once (epic #14, D4).** `GPURenderDataSource` is where a GPU outcome gets its meaning. Each `render` hops onto the `FrameExecutor` first, because the surface pool it resolves the two leases through is confined there; a lease that no longer resolves is `.invalidResource` before any gateway is asked for anything (no context, no binding, no command buffer). It then binds input (texture 0) and output (texture 1), commits exactly one `ComputePass` over a grid covering the output surface, and maps the completion with the pure `GPUCompletionMapping`. Failures before the commit split by cause: a surface that cannot be bound is `.invalidResource`, a GPU runtime that cannot take the pass (no context, no encoder, a foreign library handle) is `.internalError`, and both are logged because the mapping drops the gateway's error. A raw code counts only in `MTLCommandBufferErrorDomain` — the same number from another domain is `unknown(code:)`, never misread as a timeout. Every texture bound for a pass is unbound exactly once on every path: at once when a later bind or the encode fails, otherwise from the command buffer's completion, so the bindings live exactly as long as the GPU reads the surfaces; `FakeTextureCacheGateway.isBalanced` proves it under any completion order (a 50-seed property test). The GPU context is made on the first pass and kept; a failed `makeContext` is not remembered, so a later pass asks again. A caller's cancellation does not cut a pass short — a committed command buffer cannot be withdrawn, so the caller waits for its completion, keeps both leases until `render` returns (the renderer never releases one), and the textures still go back; the `GPURenderer` port states this, and `FakeGPURenderer` behaves the same so a Repository suite cannot be written against a cancelled render that returns early. The DataSource keeps no failure history: per-frame pass-through is the pipeline's (#22), and counting, budget and auto-disable are `EffectHealthPolicy`'s (*Effect health* below). **No uniform byte packer:** `MetalGateway` hands `EffectUniforms` itself to `setBytes` at index 0 with its stride (the effect's own parameter block, at index 1, is the other case: its layout comes from the manifest, so `ParameterPacker` packs it, *Effect parameters* below), so the packing is the struct's memory; a seeded property test reads the bytes a pass carries at the MSL offsets (0 / 4 / 8 / 12 / 16, stride 24) for arbitrary bit patterns instead of maintaining a second, parallel encoding.

**Effect parameters: a generated `Parameters` struct at buffer 1, one layout for both sides, and a value that reaches the next frame without a compile (#75–#78, #107).** Owner: `EffectCatalogUseCase` (the session's `setParameter`, the pure `ParameterPacker` and `ParameterReconciliation`) over `EffectRuntimeRepository`; the contract is `docs/hackathon/mvp-cd/specs/parameters.md`. *The ABI.* A manifest's `parameters` (at most 32, each a `float`, `int`, `bool`, `color`, `vec2` or `choice`; `EffectParameterValidation` rejects the package as `manifestInvalid` naming `parameters[i].<key>`) become a `Parameters` struct that `ShaderSourceAssembly` writes as **one** generated line between the prelude and the `#line` directive (`// no parameters` when there are none), so the author's first line stays at the same assembled line for every effect; the author writes `constant Parameters& params [[buffer(1)]]` and reads `params.strength`, and the uniforms stay at buffer 0. Alternative not taken: an engine-owned fixed slot array, whose indices an author would have to remember and whose reorder would change meaning silently. *One layout, two readers.* The field list is an Entity value, `EffectParameterLayout`, because the packer (a UseCase) and the source assembly (a DataSource) may not import each other, and a table per side is the drift this design exists to prevent; the generated line ends in a `static_assert` of `sizeof(Parameters)` against the layout's stride, so a drift is a compile error of the effect. *The block.* `EffectParameterBlock` is at least 16 bytes: an effect without parameters binds a zero block, so `MetalGateway` keeps one `setBytes(…, index: 1)` with no branch (`setBytes` of length 0 is invalid, and a coverage-ignored Gateway may not branch); 32 parameters are 512 bytes at the most, which `setBytes` copies at encode time, so no buffer lifetime exists to manage. *The value's way.* `setParameter` clamps and snaps in pure Swift (the control is never trusted), packs, publishes the state and hands the block to the runtime in one turn with no suspension; it never calls `prepare`, because the compile cache is keyed by `(source, options, layout)`, so a label or a default changing recompiles nothing and a slider moves the very next admitted frame. The state reads the block by value when it admits a frame, so a pass never sees half an update, and a write for an effect other than the newest one begun is dropped. The seed is drawn once per session there too (*Effect runtime* above). *Persistence.* One key per effect, `effect.parameters.v1.<origin>:<key>`, written 500 ms after the last change on `\.continuousClock` (latest wins, `PendingParameterWrites`) and reconciled with the manifest on read: ids the manifest dropped are gone, new ones and ones whose type changed take their default, the rest are clamped to the new range. *UI.* A window of its own, `ParameterPanelWindow` behind `ParameterWindow` (the picker's precedent), over `ParameterPanelPresenter` and opened by the menu's *Adjust Effect…*, which is disabled unless the chosen effect has parameters; a slider cannot live in the `.menu`-style `MenuBarExtra`, and the `.window` style would redo the whole menu.

**Effect health: the runtime reports every pass, the catalog UseCase judges, and a switched-off effect is remembered by what it compiled to (#75, #79, #122, #123, #130, #137).** Owner: `EffectCatalogUseCase` (the pure `EffectHealthPolicy` and the health half of `EffectCatalogSession`), fed by `EffectRuntimeRepository.outcomes()`; the contract is `docs/hackathon/mvp-cd/specs/health.md`. *Who judges.* Not the pipeline, which keeps no failure memory by design and must not learn that effects exist, and not the state DataSource, since policy does not belong below the Repository. `EffectRuntimeRepositoryImpl.apply` still answers the pipeline `Result<Void, EffectFailure>` and, before narrowing the result, reports an `EffectPassOutcome(fingerprint:result:)` to a stream that lives in the executor-confined state (`bufferingNewest(64)`: a slow observer loses old outcomes, never frames). *Identity.* The outcome carries the `EffectFingerprint` stamped when `admit` answers: a hand-written FNV-1a-64 over the source, the compile options and the parameter layout (never `Hasher`, which is seeded per process, since the value is persisted), so a pass admitted under effect A that ends after the user chose B still counts for A, and labels, defaults and the display name change nothing. *The policy.* Counted: `timeout`, `pageFault`, `outOfMemory`, `unknown` and `accessRevoked`; not counted: `compileFailed` (already final and shown), `invalidResource` and `internalError` (the runtime's own). Five consecutive counted failures, or thirty consecutive passes over 0.1 s of GPU time, switch the effect off; `accessRevoked` does not wait for a streak, and a `GPUTiming` of zero means no data, never fast. The policy reads no clock: it names a cool-down (300 s, doubled after each failed trial, capped at 3600 s) that the session waits out on `\.continuousClock` before preparing the effect again for one trial pass judged alone (the half-open state of a circuit breaker). `timeout`, `pageFault` and `accessRevoked` never retry by themselves, because a retried hang stalls the user's call again: they need an edit or an explicit re-enable (`EffectHealthPolicy.retryAfter(for:cooldown:)` is the one switch should that be revisited). *The record.* The disabled set is one JSON value (`disabledEffects.v1`): effect id, fingerprint, reason and whether it retries. It is written **before** the runtime is switched to the bundled effect, so a crash loop cannot repeat at launch, and a launch whose chosen effect has a record prepares the bundled effect instead. The choice itself is not rewritten: the effect stays chosen, and its menu row shows the reason and a button to choose it again. A listing lifts a record whose fingerprint no longer matches the package, so an edit re-enables; keying by id alone was rejected because it would leave a fixed shader switched off. The bundled effect is never switched off: when it fails too, the state says the GPU is unavailable. Choosing the next or previous effect skips switched-off ones (`selectAdjacent`).

**Foundation allowed in Entity/Domain.** lyra's "Domain has no Foundation" rule is not carried over — lyra itself imports Foundation in nine Domain files, and the line worth defending is OS frameworks, which the lint enforces instead.

**Three DI targets.** The extension must not link host-only implementations (Metal, AVFoundation, SwiftUI). `CommonDependencyInjection` registers what both processes share (surface pool, Mach, log, host time); `HostDependencyInjection` and `ExtensionDependencyInjection` add the rest. One wiring point per process preserves lyra's "single registration site" intent.

**Shared `TestDoubles` target.** Gateway fakes are used by DataSource, UseCase and integration suites; duplicating them per suite drifts. Doubles used by one suite stay private to it. No test implementation lives in production targets (decoy's `InMemory*` live modules are not copied).

**Seeded property tests via `@Test(arguments:)`.** No external PBT library. `forAll(seeds:)` runs its body over `standardSeeds` (0..<32); `Seeds.range(0..<N)` (in `Tests/TestSupport`) names a wider or different seed set for `@Test(arguments:)`, so each seed is a separate, parallel test case; nightly widens the range. Targets: parameter clamping, uniform layout alignment (the bytes a pass hands to `setBytes` against the MSL `Uniforms` offsets), bind/unbind balance and answer attribution under any completion order, manifest encode/decode round-trip, the stored form of an `EffectID` (`StoredEffectID`), hash-noise determinism and range, source assembly line mapping, health state machine monotonicity, surface pool invariants, PTS monotonicity (including the relay's slate/real interleaving), debounce coalescing (`EffectWatchDataSourceImpl`: one element per burst over gaps that straddle the quiet period), preview exactly-once completion with latest-wins and one draw in flight, the effect picker's grid (`EffectPickerGeometry`: the most columns of the minimum width that fit between the insets, from 1 to 32, and cells and gaps that fill the row), and the pipeline's leases under any order of effect answer, send, preview completion and stop.

**Mach receive loop lives in the DataSource; host death has two detectors.** decoy's blocking `while mach_msg` loop inside the gateway would violate the thin-live rule and saturate the cooperative pool. `MachMessageGateway.receive(on:)` returns one `IncomingMessage` (async, cancellable by destroying the receive right) and `FrameReceiverDataSource` owns the loop. The wire has three message shapes: a frame (`msgh_id` 0x10001), the host's *hello* (0x10002, carries the host's presence send right) and the kernel's dead-name notification (`msgh_id` 72, accepted only at its fixed 36-byte size and non-complex); the kernel's port-deleted (65) and send-once (71) notices, accepted only at their fixed sizes and non-complex, decode to `.notice` and are ignored; anything else is `.malformedMessage`. **Primary detector, frame gap:** a watchdog on `\.continuousClock` wakes every `frameGap / 4` (default gap 2 s), so a host that is stopped, hung or killed without the kernel noticing is declared lost within 1.25 × `frameGap`. The gap is counted from the last frame, or from the moment the receiver starts listening while no host has been seen yet (`awaitingFirstHost`, cleared by the first frame or any loss; a hello only restarts the count, since a host that greets and then never sends is still absent), so a host that never launches is declared lost once, with `hostLost(.frameGap)`, and the relay enters the slate instead of leaving the client with no frames; `hostConnected` still fires on the first frame after start and after every loss. **Secondary detector, dead-name:** after look-up the host allocates a presence receive right, announces the send right in a hello and keeps the receive right; the extension requests a dead-name notification for the right it received, delivered to its own service port, so the notification arrives through the same receive loop. A dead-name counts only when the name matches the right currently held (a stale or foreign name is ignored); a new hello deallocates the previous right (a replacing host), which makes the kernel send a port-deleted notice (`.notice`); the matching dead name is released with `releaseDeadName` (`mach_port_get_refs` + `mach_port_mod_refs`; `mach_port_destroy` is deprecated) because the notification adds a user reference of its own; a failed notification request is logged, the right deallocated and no event raised. An explicit disconnect and `destinationLost` release the presence receive right on the host and reach the extension as a dead name. A replacing connect does not raise `hostLost`: the new hello is sent before the old right is given up, so the extension adopts it first and then ignores the old name. Either detector yields `hostLost`; hello and dead-name never end the loop, but `hostLost(.receiveFailed)` does (the run ends and relaunching is the caller's job). A full destination queue is not a loss: `MACH_SEND_TIMED_OUT` becomes `MachError.queueFull`, the frame is dropped as `.queueFull` and the link is kept. **Not yet measured on a device (issue #3):** `kill -9` of the host is expected to fire dead-name first (the kernel destroys the presence receive right at once) with the frame gap as backstop; `kill -STOP` leaves the right alive, so only the frame gap can fire; `kill -CONT` resumes frames and the relay leaves the slate on the first newer real frame. The recipe is in `.claude/rules/dev-verification.md`.

**Host absence and slate.** Owner: `ExtensionRelayUseCase`, with the pure value type `SlateSchedule` (`live(lastEmitted)` / `slate(base, next, lastEmitted)`). On *any* `hostLost` the relay enters the slate regardless of whether a client is currently streaming — a deliberate simplification: nothing has to be re-evaluated on `streamStarted`, and a client that opens during the slate sees black at once; frames that find no client count in `framesDropped`. The slate PTS base is `max(hostTime.now(), lastEmitted + frameDuration)`, never behind the last real PTS, and slate frame *n* is stamped `base + n × (1/fps)` (`FrameRate.slateTime`). One black surface is allocated per slate episode (`surfaceRepository.allocate(descriptor, filledWith: 0)`), reused by every tick of the episode and released when it ends; if the allocation fails the relay logs an error, starts no scheduler and retries on the next `hostLost`. `FrameScheduler` ticks send the slate frames (`stats.slateFrames`, shown as `slate=<n>` in the one-line summary). The first real frame ends the slate: scheduler stopped, slate token released, the frame relayed. **Real PTS is re-based, not dropped:** slate PTS follows wall-clock time while a real frame carries its capture time (older by the camera latency), so a real PTS can sit below the last slate PTS for good. The resuming frame therefore sets `shift = lastEmitted + 1 ns − pts` (0 when it is already ahead) and every real frame is relayed at `pts + shift` until the next episode recomputes it; the stream's PTS stays strictly increasing and a laggy camera recovers. Only a frame whose shifted PTS does not advance is dropped as `.nonMonotonic`. When `run` ends, `defer` stops the scheduler and releases everything, so `liveCount == 0`.

**Host reconnect.** Owner: `FramePipelineUseCase` (a UseCase-owned task, not the transport). `destinationLost` starts one reconnect through the `WorkRunner` port (the frame path never starts an unstructured `Task` itself; state transitions stay on the `FrameExecutor`, the port owns only the async work's lifetime and hands back a `WorkHandle`). That work calls `virtualCameraSink.connect()` (its retry policy sleeps on `\.continuousClock`). `PipelinePhase` (`idle, connecting, connected, disconnected, reconnecting, stopped`; implementation-only, a `CurrentValueSubject`) makes the state testable. A loss that arrives while connecting or reconnecting is remembered and replayed after the attempt settles; repeated losses without a `.sent` in between back off with `RetryPolicy.serviceLookup` delays (250 ms doubling to 5 s), so a flapping extension is not hammered. An explicit disconnect or a `lookupFailed` never reconnects, and `stop()` cancels the work through its handle, which ends a back-off sleep with `CancellationError` so a later clock advance never reconnects. When a connect replaces a live link, the transport announces the new presence right *before* it gives back the old port and presence; a failed announce is logged and the link stays up.

**Install transitions.** The `SystemExtensionGateway` delegate yields raw events with no interpretation (`.failed(code:description:)`, `.willReplaceExisting`, and it always answers `.replace`); `ExtensionInstallDataSource` maps `OSSystemExtensionError` codes in one pure function: 10 (forbidden by system policy) → `denied`; 11, 12 (request canceled / superseded) → `canceled`; 2–9 (missing entitlement, unsupported parent bundle location, extension not found, extension missing identifier, duplicate extension identifier, unknown extension category, invalid code signature, validation failed) → `invalidBuild(code:)`; anything else → `other(code:description:)`. `.willReplaceExisting` re-yields `installing` only while installing (during `needsApproval` it is only logged). A stream that ends without a result is `failed(.other(code: -1, …))`. A generation counter on `drive()` keeps the events of a superseded request (after `retryAfterFailure`) from touching the new one.

**System integrations: the gateway reports, the DataSource decides (#176, #177, #178, #179).** `LoginItemGatewayImpl` and `HotkeyGatewayImpl` are coverage-ignored and thin (*Thin shells, thin lives*), so every decision about them is a DataSource's and is proven against the fake. *Login item.* The gateway answers the raw `SMAppService.Status` as an `Int` and lets `register` / `unregister` throw what the system throws; `LoginItemDataSourceImpl` maps 0, 1 and 2 to `.off`, `.on` and `.needsApproval` and every other value (3, `notFound`, included) to `.unavailable`, so a raw value this build does not know is a status the app cannot act on, not a crash; it calls `register` only from `.off` and `unregister` only from `.on` or `.needsApproval`, so a repeated toggle never reaches the system; a throw is logged once (`launch at login:`) and never leaves it, and `setEnabled` returns the status read back, so the caller sees what is in place. *Hotkeys.* `HotkeyGateway` has two calls, both `@MainActor` because Carbon calls back on the main thread: `observePresses` installs one handler on the application event target and `register(id:keyCode:modifiers:)` asks the OS for one hotkey; each returns a `HotkeyHandle` that carries the OS status and that its owner releases exactly once, and a refused registration still returns a handle, released like any other. `HotkeyDataSourceImpl` (`@MainActor`, a class) owns the registry: a `register` releases the hotkeys of the call before it, installs the press observer when none is installed (once for the life of the process; an observer the OS refuses leaves nothing registered, and the next `register` asks again), asks for each binding, releases a refused one at once, logs it and lists it in `failed`; the id the OS reports is the `HotkeyAction`'s raw value, and a press of an id no action has is dropped. A stream from `presses()` ends the one before it, so one subscriber is served at a time.

**Service-name triple.** The Mach service name is declared once in `ProductIdentity`; host entitlements (`mach-lookup`), extension entitlements (`mach-register`) and the constant must agree or `bootstrap_look_up` fails silently (decoy). `scripts/check-service-names.sh` (in `make check`) compares the three.

**Thin shells, thin lives.** `Apps/**` holds only `main.swift` and assets, plus the generated `Info.plist` / entitlements (`scripts/check-shell-thin.sh` bounds line counts and file kinds). Coverage-ignored Gateway modules obey decoy's thin-live rule: ≤ 50 lines per file, no `if`/`guard`/`switch`/`for`, no `var` (`scripts/check-live-thin.sh`), and so does the one coverage-ignored file outside a Gateway that is not plain wiring, `DevelopmentSubstitutions.swift` in `HostDependencyInjection`. `FileSystemGateway`, `FileWatchGateway`, `ImageIOGateway`, `AppDirectories`, `HostEnvironment` and `StandardStreams` run in the coverage run (their smoke suites are real), so the script does not police them; they are written to the same rule by hand.

**Coverage.** codecov as lyra (`project: auto / 1%`, `patch: 80%`). Ignored: `Domain`, the three DI targets, `Views`, `Apps/**`, and the Gateway modules whose real backend is not exercised in the coverage run — `MachGateway`, `SystemExtensionGateway`, `CMIOExtensionGateway`, `AVFoundationGateway` (no extension, camera or CMIO on a runner), `WorkspaceGateway` (opening Finder is a side effect nothing on a runner can observe), `HotkeyGateway` (a hotkey cannot be pressed on a runner, and a session without a window server may refuse it), `LoginItemGateway` (registering would change the login items of the machine, so its smoke only reads the status), `LogStoreGateway` (a log store cannot be read on a runner) and `MetalGateway`, `MetalKitPreviewGateway` (GPU suites run in their own process and never feed codecov, even though the runner has a Metal device) — fixed, never environment-conditional. GPU suites run in `make test-gpu` outside coverage. `DevHarness` is covered, like `App`: `HarnessSession` runs under `DevHarnessTests` (its behaviour is `HarnessInteractor`'s and `FramePipelineUseCase`'s, each with its own suite, and `HarnessWiringTests` runs the pair over fakes), and `HarnessMenu` (the main menu, and the Router's start and stop) runs under it too; the AppKit glue around them (`main.swift`, `HarnessAppDelegate`) stays a few untested lines.

**Decoy lessons carried as ADRs.** (1) IOSurface across actor boundaries crashes on Swift 6.3 → leases + no actors. (2) Service-name triple → lint. (3) `CMIOExtensionStream` needs `.hostTime` clock and real mach-uptime PTS. (4) `needsApproval` must be surfaced in UI with a Settings deep link; the app must sit under `/Applications` for activation. (5) Two Developer ID provisioning profiles are required; the release workflow had never run end-to-end in decoy.

**The extension's entry point resolves the relay UseCase.** The Interactor, Presenter and View lanes exist for the GUI (the ADR above); the extension process has no GUI, so it has none of them, and `ExtensionDependencyInjection` registers the relay UseCase and the layers beneath it only. `ExtensionApp` therefore resolves `\.extensionRelayUseCase` directly — the one Entry → UseCase edge in the graph — and the key-path lint carries it as a named, permanent exception. A pass-through Interactor was rejected: the pass-through Repositories (`ExtensionInstallRepository`, `PreviewRepository`) keep a layer every process has, whereas an extension Interactor would add a GUI lane to a process that has no GUI.
